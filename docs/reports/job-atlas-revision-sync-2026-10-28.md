# 岗位地图：revision 增量同步验收

日期：2026-10-28。环境：macOS arm64、Node v26.7.0。压测全部使用合成岗位与独占临时 SQLite，不向真实招聘网站发起采集，也不把测试岗位导入用户库。

## 结论与范围

已有完整基线后的刷新已改为基于 `{ epoch, revision }` 的净增量同步，覆盖实际入库以及服务自主执行的地区 / 企业补全。HTTP、浏览器 Worker 和页面之间都只传变更实体；没有变化时复用同一个快照对象，不再重新下载、解析或回传整库。

5000 / 15000 岗的实际服务生命周期、HTTP、SQLite、计算 Worker 和真实浏览器地图回放均通过。连续入库三批、每批 16 岗并等待自动补全，实际服务 + Worker 测试的同步流量均为 183009 字节；浏览器另一组合成样本均为 189537 字节。首次基线之后没有再次整库下载，最终增量结果与完整导出、参考查询一致。

本阶段只处理同步协议、耐久变更标记与浏览器增量安装，不调整查询索引、采集权限、地图精度或 UI 动画。完整入库 / 补全 / 查询流程仍有明显耗时，15000 岗浏览器样本约 49 秒，且有两次超过 50ms 的主线程长任务，不能宣称零卡顿或采集已瞬时完成。

## 三个独立边界

| 边界 | 实现 | 不承担的职责 |
| --- | --- | --- |
| 公共同步契约 | `dataset-sync-contract.ts` 定义完整基线、增量、无变化响应及严格校验；纯数据契约不引用 SQLite、HTTP、UI 或查询实现 | 不建立搜索索引，不改变岗位证据含义 |
| 耐久同步读取 | `dataset-sync.ts` 管理 SQLite 实体变更标记、epoch、revision 窗口和有界读取；由 repository 在原事实事务内标记变更 | 不新增写入队列，不触发补全，不改变 revision |
| 浏览器同步 / 安装 | `snapshot-sync.ts` 管理每个认证连接的基线和游标，计算 Worker 验证并合并，页面分块接收变更 | 不修改采集调度、工作区布局、动画或既有查询算法 |

### 服务端协议与一致性

- 新增只读认证入口 `POST /api/v1/dataset/sync`，沿用 Bearer、Origin / Host、请求预算与只读 WAL 计算线程。
- 首次请求 `{}` 返回 `snapshot`；后续请求 `{ cursor: { epoch, revision } }` 返回 `delta` 或 `unchanged`。`delta` 包含 `from` / `to`、八类公共实体的 `upserts` / `deletes`。
- SQLite V6 中，每个实体只保留最近一次变更标记；标记与实体、删除、耐久幂等回执和 revision 一起提交，失败回滚不留下可见标记。
- 同步读取在同一个只读事务内取得游标与实体。仅对 revision 索引选出的有界变更 ID 做主键读取；无变化路径不读取公共表，也不进行整库公共投影。
- 保留最近 512 个 revision。首次连接、窗口断档、epoch 不同、游标超前或增量超过 4096 个实体 / 4 MiB 时，返回明确原因的完整基线，不截断增量冒充完整。
- V5 → V6 迁移建立当前版本基线，不重写历史岗位。普通服务重启保持 epoch；完整备份恢复建立新 epoch，避免把另一个仓库或恢复前的游标误用到当前库。
- 地区 / 企业补全、人工覆盖、合并删除与拆分均进入相同协议。历史推测办公室的公开隔离投影及相关观察警告与完整导出一致；仍不把城市参考点或推测地点当真实办公坐标。

### 浏览器与页面安装

- 同一端点、令牌和响应预算共享串行 revision 流，不跨认证连接继承游标。基线缓存有三份上限。
- Worker 内严格校验响应、游标衔接及完整引用关系；只对变化表创建新数组，未变行和未变表保持对象身份。页面不再对每轮完整数据做第二次 Zod 克隆和全局引用检查。
- Worker → 页面仍按 128 行分块并等待确认。增量分块先暂存，按表应用时让出主线程，完整安装后才发布新版本；列表和地图不会看到半次传输。
- 无变化时返回原快照对象且没有实体块回传。页面缓存淘汰或传输取消后，可以从 Worker 中已校验的基线修复本地安装，无需再次通过 HTTP 下载整库。
- 并发刷新合并同一读取。单个观察者取消不会取消其他观察者；只有最后一个观察者取消时才中止底层读取。错误、取消或损坏响应不会推进游标，也不覆盖上一份可用结果。
- 保留旧 `GET /api/v1/dataset/export`。仅当同步入口明确返回 404 / 405 时临时兼容旧服务，30 秒后重新探测；认证、网络与格式错误不伪装成协议不支持。
- 既有采集流水线和后台补全刷新继续调用原 `readAtlasSnapshot` 入口，自动获得增量结果，无需用户手动补全或刷新地图。页面刷新丢失 Worker 基线后仍需一次完整初始化，不能只持久化一个 revision 就应用增量。

## 明确保留的限制与后续边界

1. 首次连接、页面刷新失去基线或增量断档仍需一次完整快照；仍有 64 MiB 上限。15000 岗本次初次同步约 10 秒，后续可独立设计分页 / 流式初始化，不能用截断解决。
2. Worker 仍对新版本做完整引用一致性校验；变化表的浅数组重建也不是 O(delta)。本阶段减少重复下载、整库解析和结构化复制，不代表所有 CPU / 内存工作都只与新增量有关。
3. 既有入库全库投影、补全投影和查询算法继续在计算线程运行。15000 岗三批完整流程仍约 49–52 秒，后续应独立测量和优化，不与同步协议或动画合并交付。
4. 继续单独 profile 地图提交、绘制和 GC，覆盖更分散的办公点、真实底图及较弱硬件，定位 66ms 长任务。
5. 查询索引、UI 质感、动画、3D 和生图仍是各自独立阶段；本轮没有实施。
