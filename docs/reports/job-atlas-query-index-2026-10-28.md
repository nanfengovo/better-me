## 实现

- 新增 `createJobQueryIndex(snapshot).search(query, options)`：每份不可变快照只做一次数据校验、关系映射与有限字段倒排索引；整库查询指纹按快照复用。
- 文本索引惰性准备：无关键词展示岗位时不标准化完整 JD；企业/岗位 ID 等筛选先缩小候选集合，再准备必要文本。
- 跨结构共享的 revision 用弱引用复用未变化岗位、企业、地点的标准化文本；不以 revision 数字作为跨库缓存身份。
- 匹配集合与排序/地图聚合使用两层缓存，分别限制为 8 项。分页只切片，排序或地图级别变化不重新执行完整文本匹配。
- 模糊匹配共享同一次查询的词语编辑距离判定，每个候选词缓存上限 4096 项，不使用全局无限增长词典。
- 计算 Worker 按不可变地图桶数组的身份复用 GeoJSON/几何结果，分页不重复准备相同地图数据；仍使用原有分块传输、取消和淘汰协议。
- 公共 `queryJobs` 保留无索引参考路径，索引路径与其共享权威匹配规则。C#/C++/.NET、同一办公地点上的国家与地区 AND 条件、未知薪资/距离、真实位置精度、来源覆盖和游标契约不变。
- 缓存包含实际查询上下文；UTC 评估日、汇率、配色、别名、距离锚点、城市参考批次和快照变化会使对应结果失效。失败的异步计算不会永久占用缓存。

索引输入与返回事实应视为只读；新 revision 使用新快照/索引。模块不依赖 React、DOM、SQLite、网络、服务令牌或简历存储。

### 5,000 / 15,000 岗规模结果

单位为 ms。每组单元格依次为「无索引参考中位数 / 索引首次切换该条件 / 索引暖缓存中位数」。首次切换不含已完成的快照索引准备；完整冷启动另列，避免把缓存计时当成冷启动计时。

| 场景 | 5,000 岗：参考 / 首次 / 暖缓存 | 15,000 岗：参考 / 首次 / 暖缓存 |
| --- | ---: | ---: |
| 切换新关键词 | 1068.05 / 175.43 / 1.72 | 2197.17 / 742.54 / 0.49 |
| 新的组合筛选 | 905.24 / 278.90 / 2.21 | 3189.12 / 645.75 / 1.18 |
| 相同查询下一页 | 2302.14 / 0.22 / 7.45 | 4811.87 / 0.20 / 0.92 |
| 切换地图聚合级别 | 1498.45 / 7.31 / 0.47 | 6706.07 / 23.29 / 4.32 |

完整冷索引准备 + 首次 C# 查询：5,000 岗 **1350.77 ms**，15,000 岗 **3186.54 ms**。

结构共享的新 revision 同时改 1 岗与 1 地点：两种规模都只重新标准化 **1 份完整 JD**。准备新索引 + 查询分别为 **940.03 ms / 4347.95 ms**；无索引参考查询分别为 **1555.70 ms / 6416.46 ms**。岗位、分面、地图桶、游标与参考路径逐字段一致，地图中的修改坐标也正确更新。这个结果同时说明：新 revision 的一次性准备成本仍值得下一阶段单独优化。

宿主机有其他应用运行，尤其微小缓存耗时会有调度抖动；这里不据此承诺固定延迟。最初与构建并行的一轮 Worker 测量受干扰并触发响应性门槛，未作为最终性能证据。最终成对规模测量与构建串行运行。

原始证据：隔离目录父级的 `query-index-final-scale.log`、`query-index-regressions.log`、`query-index-final-build.log`。隔离副本最终构建仍有既有大包体积和 Node 模块浏览器外部化警告，本阶段未修改这些无关问题。

## 边界与后续独立工作

缓存命中的毫秒级计时是查询计算计时，不是浏览器端到端延迟或 FPS。首次快照/新 revision 仍需一次快照校验、关系/倒排准备与整库指纹；地图桶变化仍需新的聚合与传输。它们没有被假装成零成本，也未与 UI 或网络协议改造混在本阶段。

如果继续优化，下一项可以单独研究 revision 级结构索引维护及内容指纹维护，减少每个新 revision 的一次性准备成本；另行计量 Worker 的地图结果传输，而不是用查询缓存数字代替端到端性能。
