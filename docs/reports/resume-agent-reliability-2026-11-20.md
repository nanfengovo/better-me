# 简历 Agent 可靠性实测

2026-11-20。本轮发现并修复了一处会改变用户已确认句序的缺陷。用 12 条独立于裁判输入而预先写定的合成判断校准本机模型，只有 5 条的结论和引文同时通过。对一批已有的 5 个公开来源岗位与履历配对，重新读取采集时的原任务，4 个生成了可冻结候选，1 个失败。三组数字分别描述修改流程、裁判和候选交付能力，各有自己的分母。

## 一次修改怎样验收

| 用户关心的问题 | 用什么证据判断 | 实测范围 |
|---|---|---|
| 用了哪份项目材料 | 比对最终改句、来源编号和原文，核对补充说明来自哪一个岗位和哪一次确认 | 临时简历和两组项目材料的落盘读回；公开 Gold 保留原文来源与许可。履历中的项目为作者自述。 |
| 漏了什么技术证据 | 先列出有材料支持的岗位要求，再检查覆盖情况。未选项目仍须能找回，遗漏授权字段的计划应被拒绝 | 新用例故意漏掉一个技术字段，随后验证 SQLite 独立字段在合法修改后逐字保留。Gold 另以事先标注的要求评估覆盖率。 |
| 有没有编造成果 | 对完整句子的分工、环境、数字和结果逐一比对。仅出现同一项技术不能证明所述结果 | 合成草稿的“延迟降低 90%”被拒绝。裁判曾把同事的设计归到本人。 |
| 是否理解修改意图 | 将“只改哪一句、哪些内容必须保留”预先记为验收条件，对照提案与真实保存版本 | 固定回复可重现正确提案、改错字段、夹带额外修改的系统处理。自然语言理解另按真实模型的尝试观察。 |
| 本人确认的内容还在吗 | 重开正式存储，逐句比较原稿、第一版、第二版，同时检查次序和次数 | 已修复夹带乱序或重复仍能进入待审批的问题。 |
| 多轮后是否串用上下文 | 第二个岗位沿用同一份简历，同时提供新的项目原文；主动把上轮的回答或旁边字段的答案放入引用 | 两种串用均被拒绝，成功保存的两个版本各自能追到当时的来源和回执。 |

这条回归使用正式任务执行器与临时磁盘存储。模型答复固定，验证目标是批准、拒绝、保存和读回的行为。[两轮回归](../../evals/resume-quality/revision-continuity.test.ts) · [逐句修改规则](../../apps/agent-host/src/tasks/evidence.ts) · [公开 Gold 的来源与标注](../../evals/resume-quality/gold/README.md)

**真实模型的同类任务停在了首轮。** 给本机 Gemma 一份合成简历，要求“只补 Redis 的实际动作，保留 SQLite 原句”，第二轮原计划只改 SQLite。首轮选材时模型把两项都列为相关；明确只勾选 Redis 后，它提出“执行 Redis 键过期的回放脚本，记录缓存失效的复现步骤。”文字符合本轮修改目标。补丁只引用了项目材料，漏了被改写的简历原句，Host 以 `original_resume_evidence_required` 拒绝成稿。实际发生 2 次本机模型调用、0 次工具调用、0 次写回；重开只看到原来一版，两条原文与事实库均保留。第二轮没有开始。这个案例同时说明了文字层面的意图命中、证据契约失败和原稿保护成功。[真实任务与落盘读回](../../output/resume-intent-local-20261120/observation.json) · [复现实验](../../output/resume-intent-local-20261120/README.md)

## 模型裁判在哪些地方出错

本机 `gemma4:e2b-it-qat`，模型摘要前 12 位为 `07ea59a47401`。合成集的四类标签各有 3 条。每次调用只提供本例的陈述、材料及所引编号；样本编号、预期答案、判据和其他答卷保留在评分端。一次判决必须先通过结构、逐字原句及来源范围检查。每段引文能否解释整条结论，仍可对照原始答卷逐项复核。可用性与结果吻合度分别记录。标签由开发评测预先标注，尚无外部人员复核。[原始校准集](../../evals/resume-quality/judge-calibration/cases.json) · [原始答卷与完整报告](../../output/judge-calibration-20261120/report.json)

| 预期类别 | 计划数 | 吻合 | 其他结果 |
|---|---:|---:|---|
| 所引原文支持 | 3 | 3 | — |
| 与原文有明确矛盾 | 3 | 2 | 1 条误放为支持 |
| 事实有来源，但引错了材料 | 3 | 0 | 3 条未通过引文范围检查 |
| 材料不足以定论 | 3 | 0 | 1 条误放为支持，2 条误判为明确矛盾 |

全体吻合 **5/12**。返回可计分判决 **9/12**，其中吻合 **5/9**。在 9 条不能直接通过的陈述中，**2 条仍被裁判判为支持且通过了引文结构检查**。例如，J02 原文写明字段由另一位组员设计，本人只复测，裁判甚至在理由中指出了这个矛盾，最终却给出“支持”。这解释了为什么核对引用存在和使用模型点评之后，仍应保留本人确认与人工抽查。[J02 原始模型回答](../../output/judge-calibration-20261120/J02.attempt.json)

这 12 次本机调用均返回用量，输入 **3,223 token**、输出 **1,258 token**。宿主开始请求至收到答复的 P50 为 **1.462 秒**、P95 为 **6.178 秒**。P95 采用最近秩，在 12 个观测中等于最长一次。没有采集电耗或账单。逐次请求使用结构化输出，语义仍由校准集验证。关于裁判偏好和格式约束，见[裁判评估原论文](https://arxiv.org/abs/2306.05685)和[Ollama 结构化输出说明](https://docs.ollama.com/capabilities/structured-outputs)。

## 工具权限与不可信资料

用无害格式请求作对照，把同一句话依次放进岗位描述、简历和模拟模型回复。资料仍进入原来的材料字段；越出答复契约的结果被拒，工具调用为 0，重读没有触发再次派送。其他用例核对了同意前的工具预览、修改被拒后业务数据保留、仅所选提案获准写回。这些结果覆盖指定权限与状态边界；开放式提示注入抵御率尚未测量。[文本与权限回归](../../apps/agent-host/tests/resume-replacement-contract.test.ts) · [工具同意流程](../../apps/agent-host/tests/career-mcp-client-http.test.ts)

## 从运行回执读指标

对 11 月 14 日已有的 5 例采集批次执行本地重算。本次回放新增模型请求 **0**。5/5 个案例能核对任务账本，4/5 生成了可冻结候选，另 1 例失败。未收集本人是否采纳或最终是否使用。5 次账本登记的模型尝试没有关联的供应商 token 和账单原件，费用未知。工具登记调用 0 次，成功率无分母。任务首次启动至回复或停止的实际耗时中位 **6.306 秒**，最长 **7.601 秒**，与供应商推理耗时分别记录。[完整批次报告](../../output/resume-reliability-cloud-replay-20261120/report.md)

新采集的配置模型调用会把 Host 等待返回的时间，以及供应商实际返回的输入、输出 token，关联到该任务的本次返回。报告分别显示已观测小计与覆盖率，保留单侧缺失、超时和无账单状态。使用者可为指定提供商、模型及版本传入固定输入/输出费率；只有两侧计量都齐全的调用计入费用小计，整批计量齐全后才给出全批估算。[运行指标](../../evals/resume-quality/runtime-quality.mjs) · [费用计算](../../evals/resume-quality/token-cost.mjs)
