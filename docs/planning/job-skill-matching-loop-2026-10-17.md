# 自用岗位发现、真实技能匹配与优化规划

日期：2026-10-17，Asia/Shanghai。状态：用户需求已记录，以下领域设计、展示与实施顺序为方案，尚未实现。本方案承接 `recruitment-aggregation-assessment-2026-10-17.md`，不改变当前招聘网页读取目标的执行状态。

## 用户本轮明确的产品要求

- 获取各招聘网站与公司官网的岗位信息，集中展示。
- 岗位与求职方向、技术栈标签关联，自动匹配并推送合适岗位。
- 简历导入确认或编辑保存后，与 JD 对比，呈现当前匹配情况和后续优化规划。
- 匹配必须考虑个人真实技能，不能只做简历措辞与关键词对齐。

具体来源范围、刷新频率、推送渠道、评分权重及规划时间预算尚未确定。本轮固化需求与设计，不创建实际采集任务、通知自动化或模型调用。

## 现有实现与不足

- `packages/core/src/schema/fact.ts` 已有 Experience.techStack、FactClaim.tags、用户目标和约束；标签没有统一技能实体、熟练程度定义、证据类型或逐项核实关系。
- `packages/core/src/ai/client.ts` 的 analyzeJdMatch 只接收 ProjectedResume 与单份 JD，无法回查未展示的经历。提示词称输入已通过事实库校验，但当前 Schema 校验不能证明经历和技能真实。
- `packages/core/src/ai/types.ts` 只有模型给出的 matchScore、优势/缺口字符串与改写建议，缺少 JD 原句—要求—证据—判断关系及评分版本。
- `apps/web/src/App.tsx` 向 JD 弹窗传入当前投影简历；目前并无导入/保存后自动批量重算、持久匹配报告或增量推荐机制。
- 官网来源适配与机会库已有基础；它们不是持续多源聚合。用户提供的三个原岗位均已有正式产品全文读取证据：BOSS 3175 字符（描述 3167）和 51job 393 字符各在 0/15/30 秒三次一致；猎聘 2259 字符在 0/15/30/60/120 秒五次一致，另已通过隔离来源的界面完整预览。多岗位及长期稳定性仍未验收，不能据此外推全站持续采集能力；详见 `../reports/job-browser-reading-2026-10-17.md`。

## 岗位数据获取

为每个来源设置适配器，依据其可用能力使用官方/授权接口、允许读取的公开网页、正常浏览器动态读取或用户发起的单条导入。爬虫是其中一种工具；来源限制和完整性必须单独标识。

采集与匹配分开：保存来源岗位编号、原地址、发现链、采集时间、来源时间原文、正文版本、正文完整性及最近核验结果；错误、受限和未读取不能生成空 JD 冒充成功。跨源疑似同岗先关联候选，保留各来源及冲突。一次读取失败不表示已关闭。

自用首先围绕用户选定的方向、城市、公司和来源采集，控制范围；后续选择的定时刷新需要运行中的任务进程。浏览器关闭或电脑休眠时，本地 Web 不承诺后台刷新或通知到达。

## 真实技能模型

技能标签用于发现与检索，能力判断需要具体上下文和证据。每个技能条目建议记录：

- 规范名称、别名及关系；如 C#、.NET、ASP.NET Core 有关联，但不能当成同一要求重复累计。
- 实际任务和责任范围：参与使用、独立实现、排障优化或设计决策，避免只用“精通”等模糊等级。
- 来源经历/事实条目、项目产物、用户自报或测评观察及其时间。
- 用户核实状态与证据局限；模型抽取的标签、简历文字和学习完成记录不自动证明掌握。
- 用户允许用于匹配的范围。私有匹配可以使用未展示在当前简历上的事实；外部模型调用仍只提供所需且允许使用的材料，隐藏内容不自动进入对外简历。

导入结果先进入待核对状态，用户确认的变更才改变正式能力依据。补充证据可能提高对原有能力的判断把握，不等于用户刚获得了新技能。删除和纠错证据也必须能降低或撤销先前判断。

## JD 要求与匹配报告

从原文提取岗位职责、必要要求、优先条件、经验/级别、业务领域、语言、地点/远程范围及其它明确条件。每条要求绑定 JD 快照与原句；显式要求和模型推断分开，未披露项为未知。技术标签可供检索，复杂职责保留完整语义，不压成词袋。

报告区分三个维度：

| 维度 | 对比对象 | 结果含义 |
| --- | --- | --- |
| 能力匹配 | JD 要求 vs 允许参与匹配的事实、技能与证据 | 已有依据、部分覆盖、已确认缺口或未知；说明原因及证据 |
| 简历呈现 | 当前 ResumeView vs 已有能力和 JD 要求 | 已展示、已有能力未展示、表达不清或无依据的表述 |
| 机会适配 | 岗位条件 vs 用户目标与偏好 | 明确符合、明确冲突或待确认；强约束与可协商偏好分开 |

缺口处理建议：

| 判断 | 动作 |
| --- | --- |
| 有经历依据且已展示 | 保留，准备相关面试追问 |
| 有经历依据但未展示/表达不清 | 选择真实经历、重写表达或调整投影；能力判断不因文案变化自动提高 |
| 用户自报做过、证据不足 | 追问贡献范围、补项目材料或定向检查；不直接归为不会 |
| 已确认知识或实践不足 | 安排对应练习、项目任务及验收，再更新证据 |
| 硬条件明确冲突 | 单列提示、核实或调整目标；不靠其它标签加分掩盖 |
| 要求或个人信息未知 | 展示未知及待确认问题，不按零分处理 |

评分如以百分比展示，应明确规则版本、权重、证据覆盖范围及未知项；相同输入版本应可复算。模型辅助提取和语义映射，评分由可查看的规则聚合，不让模型凭整体印象直接决定总分。相关标签/重复要求需避免重复计分。

证据不足时显示“资料不足，暂无法可靠评分”或覆盖范围，不制造精确分数。评分只服务同一规则下的比较，不是录用概率或客观认证；“Schema 合法”“用户自报”“独立测评”属于不同依据。

## 自动推荐与触发

- 新岗位或 JD 实质变化：与已保存的目标、偏好和能力版本匹配，生成带推荐原因的结果。
- 导入确认、正式事实保存、证据增删或核实状态变化：重评受影响的岗位，更新能力匹配。
- 简历选择/措辞发生变化：重评对应简历的呈现；只有来源事实确实变化才重评能力。
- 偏好变化：重排机会适配；字体、颜色和排版变化不触发能力分析。
- 结果以 JD、事实/证据、ResumeView、偏好及规则版本关联；旧结果标过期，取消/晚结果不得覆盖新版本。

保存后的本地变更检测可自动执行。云模型批量分析需在自动分析设置下限制范围、并发与预算，合并重复保存，仅分析受影响的岗位；没有绑定目标时不随意挑全库分析。关闭自动分析时保留过期提示和手动重算入口。

推荐建议分为当前可考虑的岗位和需要补强后再考虑的岗位，展示关键证据、短板与未知条件。新岗位、关键条件变化或确有价值的排名变化才通知；相同来源重复读取、微小分数波动不重复推送。首期可用应用内推荐列表；系统通知/其它渠道与后台运行方式另行细化，本轮不创建实际通知。

## 优化规划与证据回流

规划围绕一个确认的目标方向和少量代表 JD，综合缺口重要性、出现范围、用户时间和近期求职紧迫程度排序，避免把所有 JD 加分项变成必学内容。

每项建议区分整理既有证据、改简历表达、补基础知识、做实践验证或核实岗位条件。实际学习任务应有对应 JD 原句/缺口、预计投入、产物和验收标准。完成课程或改好简历不自动提高能力匹配；检查产物、记录结果并由用户核实相关事实后，才更新技能依据和岗位匹配。

计划是可接受、调整或拒绝的提案；新岗位和 JD 更新可提出修订，不静默覆盖已接受计划。不设置一个任意分数门槛阻止申请。

## 建议的领域关系与实施顺序

领域对象以 Source/SourceObservation、Job/JdSnapshot/Requirement、Skill/SkillEvidence、RequirementMatch/MatchReport、Recommendation、Gap/ImprovementProposal 和 Application/MaterialSnapshot 分工，沿用现有 TS Core/存储端口，逐步迁移与补齐备份，不把所有对象塞进简历正文或标签数组。

1. 先实现可信对比：JD 要求与原句、事实/技能证据、能力/呈现/偏好分开、持久报告和版本过期机制；不依赖全站采集。
2. 接上聚合：来源目录、关注公司、统一岗位列表、来源更新保护与同岗候选关联；用户选定范围内增量匹配。
3. 接上自动推荐：导入/保存/岗位变更触发、缓存/取消隔离、应用内结果；随后按选定运行方式接入刷新与推送。
4. 接上可验收的优化规划和证据回流；对话 Agent、契约打卡和自主执行仍按后续阶段决定。

最小验收：有依据却未展示的技能不会被误判为不会；未知不记为确定缺口；仅改措辞不提高能力判断；新增有效证据可追溯地改变结果；JD 变化标旧结果过期；同步不损坏投递/材料；推荐能解释理由且不重复通知。
