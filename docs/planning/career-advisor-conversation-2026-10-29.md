# 职业顾问式 Agent：参考机制、现状与分阶段接入设计

日期：2026-10-29。状态：研究与设计完成，**未实施应用功能**。本轮不修改简历、岗位数据、模型配置、持久记忆或运行服务；不刷新用户当前页面。本文只记录通用产品机制，不保存私人对话正文、简历内容、分享标识或个人性格结论。

## 1. 本轮参考范围与读取限制

用户希望参考的能力是：结合简历与获准使用的历史信息给出有依据的职业判断，提出真正影响决策的问题，用户提交选项后自动推进同一段对话。

五个指定分享链接均已尝试网页读取和独立临时浏览器标签读取。网页工具只返回页面外壳；浏览器加载后，五页均显示“无法加载此回复”。因此没有读到完整对话、原始简历或其背后的历史记忆，不能宣称已经逐轮复盘这些对话，也不能判断 ChatGPT 内部具体使用了哪些记忆机制。下文依据用户的文字需求、所附截图中的交互形式、当前代码及官方框架文档设计。若要逐轮对齐，仍需可读取的完整分享或脱敏导出。

本次不对用户本人做职业排序或性格评估，不将截图中其他模型的判断当作已核实事实。

## 3. 应该交付的用户体验

一段完整对话应当这样推进：

1. 用户提出岗位方向问题。先显示本轮实际采用的资料：简历版本、经许可的相关历史片段、已确认偏好；没有的明确显示“未提供/未使用”。不要求用户先完成长问卷。
2. Agent 给出暂定排序和依据，同时指出最可能改变排序的一项未知条件。每个岗位方向说明已有证据、现实门槛、主要代价、尚缺信息，不用无依据的精确匹配百分比。
3. 正文后出现一个结构化问题卡，说明“为什么问这个”。支持单选/多选、自由补充、选项不适用，以及允许时跳过；不预选或替用户作答。
4. 用户选好后点击“根据我的选择继续分析”。一次提交即展示用户的真实答案并启动下一轮；不需要复制选项到输入框，也不额外要求再点击发送。仅切换单选项时不立刻提交。
5. 后续回答解释“由于你刚确认了什么，哪些排序、筛选或建议改变了”，而非将上一轮长文重写一遍。信息足够就给行动建议，不机械地每轮追问。
6. 用户可更正判断、调整目标、补充反例。修改早期答案形成新的分析分支/版本；旧结论仍可回看，但不能继续当作当前有效建议。
7. 若用户选择搜索实际岗位，先把讨论转换成可审阅的搜索条件，再调用真实岗位查询；讨论岗位方向不等于确认具体职位仍在招聘，更不等于授权投递。

“自动继续”是对用户本次提交的响应，不是 Agent 自动扮演用户循环对话。通常先问一个最影响结论的问题，连续两三问后必须回到有用的阶段性结论；是否继续取决于信息缺口，而非固定问卷模板。

## 4. 用户画像：把可修正的理解与人格定论分开

建议把“画像”呈现为“我目前对你的理解”，至少区分四类：

- **资料记载/用户陈述**：简历或历史消息记载了什么，来源指向具体条目/消息及版本。简历自述有出处不等于经历已被第三方核验。
- **已确认偏好与约束**：本轮或获准跨会话使用的目标、城市、工作方式、薪资取舍等；记录确认时间、适用范围与版本。
- **待确认工作风格观察**：从授权片段中观察到的行为模式，附可能的其他解释和核对问题。允许回答“不准确”；不据此做心理诊断、固定人格标签或无关敏感推断。
- **建议与待验证条件**：模型推理的结论、可追溯依据、适用前提、可能推翻结论的信息。它不是新的个人事实。

新偏好与旧偏好冲突时，说明冲突并让用户选择本轮适用条件，不静默覆盖。模型自己的旧回复不能被反复检索后当成用户独立提供的证据。

当前会话中正常利用用户回答，不应每轮弹出存储确认；跨会话复用则需要明确、可见的授权。模型可以提出“是否记住这个偏好”，但未经确认的观察不能自动进入长期记忆，更不能写入简历事实库。

## 5. 模块边界与 LangGraph 的使用方式

建议以一个职业对话会话模块承接复杂度，而非继续把状态塞进两个 React 大组件：

`两个对话入口 → 同一个 CareerDialogueSession → 线程状态 / 获准证据 / 分析与问题投影`

对界面只暴露小接口：打开/读取会话、发送本轮输入、提交问题答案、订阅可展示事件。问题校验、答案去重、上下文版本、线程恢复和模型运行由模块内部负责；具体文件拆分在实施时决定，不为每个图节点再加一层无行为的服务或工厂。

需要分开的存储职责：

| 职责 | 用途 | 边界 |
| --- | --- | --- |
| Checkpointer | 同一线程的消息、当前问题、已接受答案、分析版本及恢复位置 | 不自动产生跨会话理解，也不默认保存全部原始简历与检索文本 |
| 持久化记忆/Store | 获准跨会话复用的偏好与摘要，带来源、确认状态和撤销语义 | 当前本地个人版先选择最小本地实现，不为此引入外部向量服务或多用户基础设施 |
| 来源库与按需检索 | 按本轮目的和授权返回少量相关简历/历史证据 | 不把所有聊天每轮全量拼接；摘要不能丢掉出处、冲突或授权信息 |

LangGraph 官方将线程短期记忆和跨线程 Store 分开；状态保存了某段内容，也不意味着必须把它全部发给模型。[Memory](https://docs.langchain.com/oss/javascript/langgraph/add-memory)、[Context engineering](https://docs.langchain.com/oss/javascript/langchain/context-engineering)

普通聊天可以在一轮输出结构化问题后正常结束，下一轮收到答案再运行图；只有确实暂停在图中间的任务才用 `interrupt()` 和同一线程的 `Command({ resume })`。不要把每个职业追问变成工具审批，也不要把正常多轮输入误用为 `Command({ update })`。[Interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts)

建议状态流为“准备证据 → 初步分析 → 缺口判断 → 等待输入 → 接受答案 → 更新结论”，工具执行另走授权边界。普通用户输入与 `awaiting_approval` 必须有不同的服务端命令。一次选择不能授权终端命令、简历修改或岗位投递。

模型输出采用可验证的结构，参考原生结构化输出或受支持的工具策略；必须核对实际模型和依赖的支持。若格式不合法，保留可读正文并明确无法生成交互卡，不能从 Markdown 列表猜测可执行动作。[Structured output](https://docs.langchain.com/oss/javascript/langchain/structured-output)

## 6. 问答协议、恢复与隐私的硬要求

详细类型草案见 [职业对话机制研究](../research/career-dialogue-agent-patterns-2026-10-29.md)。最少包含 `threadId / questionId / questionRevision / basisRevision / clientEventId`。

- 服务端核对线程归属、问题是否仍待答、选项 ID 和数量是否合法、资料/问题版本是否改变。客户端提供的 threadId 不是授权凭证。
- 同一次提交的双击、断网重试复用同一个提交 ID；返回已有回执，不重复添加用户消息。相同 ID 不同内容拒绝；不同 ID 的并发重复也由待答问题版本锁限制。
- 接受答案和安排后续运行需要可恢复的提交记录。模型失败时显示“答案已保存，继续分析失败”，重试恢复同一逻辑轮次，不让用户重新填表。
- 已过期卡片不悄悄修改当前画像；告知问题已更新并保留用户草稿。更正答案后，依赖旧答案的待答问题/结论失效。
- Companion 与完整工作台读取同一个会话，不在展开时另起对话。老的无状态聊天可保留，但不能伪装成有持久恢复能力。
- 现有 `sendAgentChat` 在 Host 失败后会转浏览器直连（`agent-client.ts:571`）。有状态提交不能未经核实就沿用这个回退路径：Host 可能已接受答案，换路调用会丢状态或重复生成。状态未知时先按提交 ID 查询/重连。
- UI 流只传正文、问题卡、出处投影、状态与可行动错误，不能直接转发含私人数据的完整图 `values`。
- 资料撤销或版本变化时重新检查上下文；旧摘要、checkpoint、日志/追踪和检索缓存也要纳入删除/失效策略。删除一个 Store 条目不等于完成所有副本处理。
- 不接管 ChatGPT 私人记忆或账户历史。仅使用 BetterMe 本地获准资料、用户主动提供的对话片段/导出；没有导入的历史必须明确未使用。

## 7. 界面只为这个对话闭环服务

这一阶段不与地图渲染、3D 素材、采集或查询索引优化耦合。问题卡与正文仍需可读：桌面正文和主要选项以 16px 左右为起点，保持足够行距和对比度；不要用密集的小字说明掩盖结论和当前问题。

建议每轮默认只展开“本轮结论 + 当前关键问题”，证据和历史依据折叠但可点击核对；前一轮已回答的卡片收起为答案摘要。小面板用于短答/预览，长分析可转完整工作台且保留当前位置与线程。不要默认展示执行日志、图节点术语或虚假的思考进度；流式正文与任务状态应来自真实事件，而非逐字动画伪装服务端流式能力。

## 8. 分阶段实施与独立验收

| 阶段 | 实施范围 | 必须独立证明的结果 |
| --- | --- | --- |
| A：单线程职业问答闭环 | 版本化会话、结构化问题、答案提交、自动下一轮、两入口接续、失败/重连 | 用户不复制答案；提交一次出现一个用户轮次；断网/双击/旧卡片都正确；本阶段不声称已有跨会话画像 |
| B：有来源的上下文 | 授权简历快照与相关历史片段、出处与版本、证据/偏好/观察区分、最小检索 | 能回答“这条判断依据哪段资料”；未授权字段不进入请求；缺资料时追问而不编造 |
| C：长期理解与纠错 | 本地持久化、用户许可的跨会话偏好、冲突和撤销、记忆候选审阅 | 新会话可使用已许可记忆；纠正后旧标签不继续污染回答；删除/失效覆盖派生副本 |
| D：从建议到真实岗位 | 确认搜索条件、调用现有真实岗位查询/匹配、返回来源与未知条件 | 有真实岗位 ID/来源，不把泛方向当成实聘职位；不自动改简历或投递 |

第一批验收使用合成简历/对话和确定性模型替身，不需要私人资料或真实模型费用：

1. 单选、多选、自由文本、都不符合、跳过；自然语言回答也可推进，不强制只能点选。
2. 相同输入与相同证据下，只有用户取舍变化时，结果明确说明哪些建议因此改变；不将模板长文重复当作推进。
3. 双击、超时、断网、重连、宿主重启和并发；恢复后不重复确认已接受答案。
4. 已回答/过期卡、资料版本变更、修改前一答案；旧卡不能更新当前状态。
5. 跨入口的线程一致性；未授权历史标记为未使用；未授权 canary 不出现在模型请求、UI 事件、Store、checkpoint 或追踪中。
6. 工具审批与追问分离；选择答案不能触发简历写回、终端运行或投递。真实简历/岗位存储保持不变。

本轮完成的是上述现状检查和可验收的接入设计，并新增通用机制研究报告。没有运行应用功能测试，因为没有更改应用代码；文档检查不能算作职业顾问功能验收。推荐下一批先实施 A，随后单独接 B/C，不将长期画像、工具执行和视觉改造揉成一次交付。
