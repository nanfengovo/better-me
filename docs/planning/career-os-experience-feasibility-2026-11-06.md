# BetterMe Career OS 体验与应用平台可行性

2026-11-06 · 基于 `agent-os` / `adb93a3` 的探索方案，尚未批准实施。

## 判断

方向可行，且与 BetterMe 已有的个人职业系统定位一致。应把它定义为**由统一 Agent 协助、以职业应用和可信职业资产为中心的工作环境**，而不是复制一套通用桌面操作系统。

本次用户明确提出：重做字体、颜色、按钮、文案层级与交互质感；参考 macOS、iPadOS、iOS 的平台习惯；以 Dock、应用窗口、主题和关于系统组织体验；探索 Agent 在沙箱中创造并发布新应用。具体视觉方案、完整窗口管理器、沙箱产品与部署方式仍待确认，本次讨论不授权任意代码执行、修改核心业务或发布。

三个不同概念：**Dock 是导航，应用是交互与能力的组织单位，Docker 是可能的执行基础设施之一。** 现有菜单不需要分别运行容器；手机也不需要安装 Docker。

## 产品体验建议

### 一套系统，三种设备表达

| 使用场景 | 外壳与窗口 | Agent 与任务 |
| --- | --- | --- |
| 电脑，精确指针和键盘 | Dock、系统菜单、应用内工具栏；默认专注一应用，可把岗位和简历并排；支持收起、恢复、最大化与键盘切换 | 可收起的系统侧面板；所选对象作为明确的上下文引用；任务中心统一展示等待确认与运行状态 |
| 平板，触控和横竖屏 | 精简 Dock；主应用占据主要区域，空间足够时双栏；使用可收起侧栏和 sheet，不依赖悬停 | 全高侧面板或 sheet；保证正文、输入法和确认操作可见 |
| 手机，单手与短时任务 | 单应用导航栈、少量固定底部入口和应用库；切应用保留位置，不缩小桌面窗口 | 按需展开的 Agent 页面；分享、采集待核对卡、审批和结果查看优先 |

平台适配由可用容器宽度、输入方式、文字缩放和任务需求决定，不能只用设备型号决定。手机不显示没有意义的最大化/最小化按钮，不接管系统返回手势；Web 中的窗口是工作区内视图，并非对操作系统窗口的控制。

建议第一批应用为：**简历、机会、成长、资料**；系统设置与应用库单独组织。机会中的地图、列表和投递是否拆成独立应用，通过实际跨任务使用验证。不是所有旧菜单都需要变成应用。

Agent 有全局唤起入口和完整任务视图，但它们是同一个 Agent 的不同呈现。应用启动、输入和保存等确定操作无需模型参与；Agent 离线时，职业工作区仍能正常使用。

### BetterMe 自己的特色

特色应来自“上下文和任务跨应用连续”，而非桌面装饰：选定一个目标岗位，关联一份简历和允许使用的项目证据，Agent 在同一任务中协助比较、提出修改和安排实践。切换应用后，资料授权范围与待确认结果仍清晰，不要求用户再次复制整段背景。

系统只显式共享选中的对象和获准字段，不因为切到某应用就把整个资料库交给 Agent。可以将这一组目标、对象和任务保存为工作场景；场景引用既有资产 ID，不复制一套权威业务库。

### 窗口与任务是不同生命周期

- 打开与切换：默认单击，回到上次可恢复位置；Dock 激活标记表示真实视图状态。
- 收起：回到对应 Dock 入口，保留草稿与可恢复状态；重型地图/动画在不可见时暂停无必要渲染。
- 最大化：进入专注空间，恢复时回到原布局；不承诺浏览器网页能操纵系统窗口。
- 关闭视图：按草稿策略处理，不等于删除资料或取消任务。涉及未保存内容时给出可理解的选择。
- 后台任务：需要已有范围明确的后台许可，并在任务中心可见和可停止；关闭窗口不产生新许可。
- 账户切换、撤权、应用停用：使旧代次失效，拒绝旧窗口与迟到结果继续写入。

版本、构建号、更新说明、许可和诊断进入“关于 BetterMe / 系统信息”。前端与执行端版本不同要如实显示；不在每页放版本、开发状态和技术说明。

## 视觉与交互质量基线

建议情绪是**安静、精确、有层次**。保留产品识别度，以暖灰/纸白和石墨深色为底，单一克制的品牌强调色；不要让每个应用自行发明颜色语义。

- **文字**：系统 UI 使用明确的系统字体与中文 fallback，正文建议 14–16 CSS px、手机输入以 16 CSS px 起步；这些是待原型验证的项目值，不是把 Apple pt 直接当 CSS px。辅助文字不能承担主要决策。纸张排版独立。
- **材质**：玻璃主要用于 Dock、系统栏、浮层等功能层；编辑正文和长表格采用稳定、清晰的实底。Apple 的 Materials 指南同样把 Liquid Glass 放在导航/控制层，并要求克制使用，而非铺满内容。[Apple Materials](https://developer.apple.com/design/human-interface-guidelines/materials)
- **控件**：统一主次操作、焦点环、按压、禁用、加载、错误与成功状态。原生可识别的控件语义优先，危险操作不能靠颜色单独区分。
- **文案**：直接命名对象和动作。永久副标题、重复“AI 驱动”宣传、技术提醒移入按需信息；保存失败、费用、资料外发和权限不能因此隐藏。
- **图标**：一套线条控件图标；Dock 应用图标可有克制的原创材质与体积感。首版固定少量常用应用，新增应用进入应用库，由本人选择固定，避免 Dock 无限增长。
- **动效**：按压即时反馈；打开/收起从对应入口出发且可反转；悬停放大只对精确指针生效且不推挤布局。频繁键盘切换不强制播放长动画。原型可从 160–260ms 的短过渡开始测，不作为已达成性能指标。
- **可访问性**：减少动态、减少透明度和高对比支持；触控目标建议至少 44 CSS px，完整键盘路径与焦点恢复；不拦截输入法组合输入或系统保留快捷键。普通文字对比目标至少 4.5:1，大字及非文字控件按相应 WCAG 条件验收。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)

新应用必须通过同一套组件、布局模板和文案规范获得系统外观。只给一份颜色 token 而允许生成器任意写全局 CSS，无法保证长期一致性。

## 应用平台与权限结构

```text
Career Shell：Dock / 搜索 / 窗口 / 主题 / 任务与权限 UI
    ├─ 内置应用：简历、机会、成长、资料
    └─ 获准的新应用：受控 UI 与已验证能力
          ↓ 应用上下文与受限命令
统一 Personal Career Agent（任务与能力） + Workspace Gateway（确定性校验）
          ↓ 经服务端身份、资源范围、版本与授权核对
Career Workspace：事实、简历版本、岗位、投递、证据与业务回执

独立构建/执行端：只提供受限计算与候选制品，不拥有职业资产主库
```

Agent 是贯穿系统的智能服务，不是权限最高的“内核”。UI 外壳负责交互，Workspace 负责真实业务状态，策略执行与身份校验不能由模型改写。

建议新增三个有明确职责的 Module：

1. **App Registry**：登记应用身份、不可变版本、制品摘要、入口、运行档位、权限、设备适配、数据兼容性和验证结果；同一登记驱动 Dock、搜索和应用库。
2. **App Host**：统一打开/激活/收起/恢复/关闭、错误隔离和状态保存。内置 React 与后续隔离前端使用不同 Adapter，调用方不直接实现权限、通知和窗口管理。
3. **Workspace Gateway**：提供受控读取、变更预览和确认命令。复用既有业务规则和工具契约，服务端派生 owner，校验资源、授权代次、当前版本、预算和幂等。

不需要一开始引入通用微前端平台、公共应用商店或第二个 Agent runtime。应用/版本状态、窗口可见状态、后台任务状态分别管理，不能用一个 `isRunning` 表示所有含义。

## Agent 创造应用的分级路线

**第一档，优先验证：声明式应用 + 纯计算。** Agent 生成字段、视图组合、表格/图表、比较规则与受控动作描述；平台使用可信组件渲染，纯 JSON 逻辑进入已有受限运行器。适合岗位要求变化对比器、证据整理器、准备清单。声明式数据仍需 schema、复杂度、表达式、链接和操作白名单校验，不接收任意 HTML/脚本。

**第二档：自定义前端包。** 有真实复杂交互需求再提供隔离构建与独立源域展示，经固定消息桥调用能力；不把生成模块 import 进主站，也不共享主站会话与模型密钥。

**第三档：完整后端/命令应用。** 涉及 Python、npm 安装、编译或长任务时，使用另行验收的受限容器或 VM 执行端。构建时也不能接触主仓库、用户 HOME、职业数据库、Docker socket 或真实密钥。

详细官方约束与候选方案见 [沙箱研究](../research/career-os-sandbox-primary-sources-2026-11-06.md)。其中 iframe 不能被当作可靠的 CPU 配额，Node vm 不是不可信代码安全机制，Docker 默认资源与挂载边界也需要显式配置。采用哪个运行产品，不在本轮替用户拍板。

发布必须是：需求与范围 → 规格/权限草案 → 隔离生成 → 固定制品 → 独立验证 → 合成预览 → 本人批准安装及权限 → 原子启用 → 可停用/撤权/更新。生成器不能批准自己、修改验证器或改变安全策略。升级增加权限需要重新批准。

**应用包回滚不等于职业数据回滚。** 旧包写入前需满足数据兼容条件，已接受的业务变化通过准确补偿命令撤销，不能恢复整库旧快照覆盖其他工作。

## 推荐实施关卡

| 关卡 | 交付物 | 进入下一关的条件 |
| --- | --- | --- |
| 1 体验定调 | 一套字体/色彩/组件/动效样板；“目标岗位 + 简历 + 同一 Agent”三端可交互原型 | 本人认可主要视觉与操作；常见操作更清晰，没有为桌面隐喻增加步骤 |
| 2 内置应用 Shell | 简历和岗位两个特征不同的应用、Dock/应用库、专注与并排、状态恢复、统一设置 | 业务与草稿保留；跨应用/账户切换、键盘与窄屏通过；旧导航可回退 |
| 3 受控创建闭环 | Agent 生成一个岗位快照对比应用；合成输入验证；批准后安装，重开与撤权 | 真正由生成产物驱动；验证器独立；权限增加/迟到结果/版本并发均被拒绝或正确处理 |
| 4 高自由度扩展 | 隔离前端包、独立构建/执行服务、可追溯发布与兼容回滚 | 威胁模型、资源限制、依赖供应链、网络/秘密边界和三端支持分别验收 |

前两关已是一项产品级前端重构，不应与完整应用平台、桌面打包、跨设备同步一起打包成一次改版。React/Vite/现有 Node 业务层可先保留；Electron/Tauri 与移动原生壳作为后续交付选择。

体验验收不只看“能点”：应覆盖浅深主题、中英文与真实中文字体、窄高/矮宽布局、手机输入法、200% 文字/页面缩放、错误和无权限状态、草稿恢复、动效中断、减少动态与连续切换。任务要求及 WCAG 具体适用条件要落实到测试用例，而非把截图或通过类型检查当成完成。
