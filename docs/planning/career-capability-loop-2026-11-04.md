## 1. 产品完成标准

用户提出一个职业任务；Agent 先判断可用能力，确实缺实现时补齐一项能力，在可信执行环境验证并完成任务；Workspace 按领域规则接纳结果；再次遇到相似任务时，用同一能力版本处理新输入，不重新生成工具。

核心交付物是：**首次真实生成并执行的工具、可追溯的业务结果、第二次复用同版本的记录**。能力目录、任务动画、Skill 文本或预置实现均不能单独代表闭环完成。已有能力足够时不创建工具，也是成功路径。

能力补齐服务于业务结果，不以工具数量为目标：先支持一个完整纵向场景，再扩大业务范围和执行权限。复用能力而非复用旧答案；能力变强与用户职业技能提高分别留证。

## 2. 八步如何接入业务

| 步骤 | 系统行为与业务连接 | 必须留下的结果 / 通过条件 |
| --- | --- | --- |
| 1 用户提出需求 | 对话或简历/岗位/成长/面试页面发起同一职业任务；结合用户选择的资产澄清目标、交付物、输入范围、成功标准、时限和预算 | 任务约定绑定目标及资产快照版本；不确定项可追问。报告、简历版本、学习提交、外部投递是不同交付物 |
| 2 判断已有能力 | 从当前账号可见的能力目录检索，再按输入输出、适用条件、验证有效性、依赖、授权及预算过滤；模型提出候选，可信代码复核 | 记录选择理由和能力版本，返回可用、可组合、缺输入、缺授权、暂时故障、真实能力缺口或禁止执行，不能只输出“我会/不会” |
| 3 分析缺少什么 | 把任务拆成业务动作，定位缺少的最小执行环节，比较复用、组合、代码、安装、Skill、服务的收益与权限成本 | 能力补齐方案说明现有能力为何不够、补什么、影响什么、如何验证、预算与退出方式；无授权不以换工具绕过 |
| 4 补齐能力 | 在隔离制品区构建候选方法/工具，固定版本与依赖；由可信验证器先做资格检查，再允许用于本次任务 | 可追溯候选制品及资格验证回执；生成器不能自改判分器或批准权限。失败可在约定预算内修复，否则停止，不登记可复用 |
| 5 执行任务 | 使用固定能力版本和最新有效的任务授权读取最少输入；记录每次真实尝试、调用与副作用 | 产物引用本次输入/能力/运行版本；进程结束与任务完成分开，所有分支都支持取消、限额和可解释错误 |
| 6 验证结果 | 按任务约定校验来源、覆盖、正确性、未知项；需要业务变更时再调用 Workspace 领域命令，核对实际回执 | 能力资格、本次结果、实际业务效果分别验收；无法自动判断的职业结论标参考/待核对，不由 Agent 自评变成事实 |
| 7 沉淀能力 | 资格及至少一次相符任务验收通过后，保存不可变能力版本、用法、适用条件、来源、验证证据与局限；按策略发布为可复用 | 保留失败尝试但不启用；只保留可泛化方法和合成测试，私人输入/结果/凭据不进入通用能力包。业务未采纳不等于工具实现错误 |
| 8 下次直接复用 | 新任务重新评估输入适用性、授权、依赖和预算，命中已验证版本直接执行并重新验收结果 | 同 capability/version/hash、新 inputHash 和执行记录，能力构建调用数为零；不适用或失效时重新评估，不复制旧结论 |

第4步的资格检查是安全运行新能力的前置，不替代第6步业务结果验证。对于保存报告等已明确授权的低风险写入，可以连续执行；采用个人事实、变更正式计划、发送材料或真实投递仍按对应业务规则处理，不能把所有动作统一成一个“同意 Agent”开关。

### 能力评估的分流规则

- **可直接使用**：契约、版本、验证与当前授权全部满足；执行现有能力。
- **可组合**：已有能力的输入输出兼容，组合后仍满足预算与权限；验证组合流程。所需权限为依赖权限的并集，不因包装成 Skill 变小。
- **缺输入/缺证据**：向用户索取具体材料或调整可接受结果；不能通过写代码制造事实。
- **缺授权**：请求最小必要授权，拒绝后保留任务停点；换提供方或自建工具不改变这个结论。
- **暂时不可用**：依赖故障、限流、额度、登录失效；有限重试或告知替代方案，不自动改收费通道。
- **真实执行能力缺口**：已定义的任务确实没有适用实现，进入补齐方案。
- **禁止/不支持执行**：违反业务真实性、政策或当前执行隔离条件；解释限制并提供安全的人工路径。

## 3. 五类补齐方式，使用同一条生命周期

| 方式 | 适合解决的问题 | 补齐后的实物与验证 | 业务例子 |
| --- | --- | --- | --- |
| 组合现有能力 | 单个工具都有，但缺少协同流程 | 版本化组合配方、输入输出映射、端到端样例；每一步沿用自己的授权 | 读 JD → 取授权事实 → 比较 → 生成岗位简历提案 |
| 编写代码工具 | 缺少可明确描述、可测试的转换/计算/检查 | 源码及 hash、固定入口、合成测试、资格与任务结果回执 | 特定岗位导出格式适配器、材料版本差异工具 |
| 创建 Skill | 缺少可重复的方法、顺序、判断与验收说明 | 绑定实际工具/契约的步骤说明、触发条件、示例和局限；做流程验收 | 项目证据核对、面试复盘方法；仅写 Markdown 不等于新执行能力 |
| 安装/接入已有工具 | 成熟实现可以补齐，但当前环境缺少 | 固定来源/许可/版本/依赖、隔离安装清单、包装器、资源测试与业务样例 | 特定文件解析、受控语言练习运行器；不全局修改用户环境 |
| 调用外部服务 | 本地无法或不宜承担的专门能力 | 连接 Adapter、数据/费用授权、错误与质量测试、服务回执；秘密另存 | 语音转录、受控远程实践执行，或授权邮箱读取 |

选择依据为任务适用性、可信度、最小权限、成本与可维护性，不固定“总是先写代码”或“总是安装”。新的第三方依赖/服务进入实施前，单独核对官方能力、维护、许可与实际适配；本轮未选定或安装新的运行引擎、工具和服务。

## 4. 与 BetterMe 五条业务线结合

以下“缺口”是情景示例，实施时必须由目录检查证实，不能把已有功能重新包装为新能力。

| 业务需求 | 已有能力可复用 | 缺口与补齐 | 验证产物 → Workspace 接纳 → 后续复用 |
| --- | --- | --- | --- |
| 经历证据/简历：从项目材料整理有依据的个人经历 | 受控取证、项目理解/确认、伴写提案、原文冲突和版本保护 | 新工单/发布记录格式无法提取：生成格式适配器，组合取证流程，沉淀核对 Skill | 事件—原文引用与冲突表；项目背景不等于个人贡献，经本人核实再形成 Fact/简历提案并保留版本；下次复用解析方法，重新核实贡献 |
| 岗位/JD/匹配：比较目标岗位要求变化 | 岗位读取、来源/快照、收藏、JD 分析入口 | 新导出格式/确定性差异环节缺失：生成转换或比较工具 | 同岗依据、要求增删、原句与不确定项；先存私有分析报告，另有授权职业技能证据才能比较个人能力/呈现/偏好；下批同格式复用工具 |
| 成长实践：完成一次针对缺口的可验收实验 | 目标确认、计划采纳、提交/反馈、固定 JS 练习和计划修订 | 新语言/实验没有运行与检查能力：构建练习包、数据生成器、受控运行 Adapter，必要时授权执行服务 | 实际代码/输出/环境与测试回执；作为学习提交与证据，不自动认证掌握或改写简历；复用运行器/检查方法，用新题与新输入复测 |
| 面试：按指定岗位完成一次口头项目面试 | 文字面试、实际原答、自适应追问、逐轮反馈 | 缺语音输入/时间对齐：接转录服务，必要时生成字幕/音频格式转换工具 | 可回放原答、时间引用、转录纠正与参考评价；归入同场次，改计划另出提案；下场复用能力但使用本次原答 |
| 投递跟进：整理授权招聘消息和待办 | 私人机会库、实际沟通/投递确认、下一步与材料快照 | 缺消息来源连接、事件解析与关联：接授权邮箱读取，生成通知格式解析器，组合核对 Skill | 来源消息、时间、岗位候选关联与重复项；本人确认真实沟通后入库，草稿不冒充已发送；新消息复用解析/去重，不自动重复联系 |

五条业务线共享能力生命周期，但业务验收不同：简历看事实与版本，岗位看来源与覆盖，实践看真实提交，面试看原答与引用，投递看实际发生和外部回执。一次工具通过不能让这些业务状态一起“通过”。

## 5. 首个 MVP：新格式岗位快照 → 可追溯要求变化报告

### 5.1 用户任务与范围

“比较这两批我授权的岗位导出资料，指出同一岗位的结构化要求变化，保留来源，保存一份私人报告。”

首轮用合成结构化 JSON 导出，不扩大到任意 PDF/OCR、登录抓取、全站采集或个人技能推断。假设字段位置/命名有两种格式，标准输出保留来源命名空间、源岗位编号、快照时间、原要求文本及输入位置。同岗身份键固定为“来源命名空间＋源岗位ID”，命名空间按来源协议必要时包含公司/招聘board。不同来源同编号、同标题/公司都不直接配对，跨源关系、缺ID和重复冲突进入待核对；两种输入格式不代表同一来源。

本批未出现只能表示“本批未见”，不能认定岗位关闭。文本增删只能表示要求文本变化；否定句、条件变化和同义判断需要另行语义核对，不包装为确定的市场趋势。

### 5.2 第一遍：必须有实际生成与执行

1. 固化任务约定和两批输入版本。检查能力目录，证明所需格式尚无适用转换能力；如果已经支持，进入复用路径，并使用另一个明确未覆盖的合成规格验证创建路径。
2. 固化转换输入输出规范和可信验收集。生成器只拿规范、合成示例和必要错误反馈，不拿真实履历、凭据或可修改的判分器。
3. Agent 使用用户明确选择且有本轮预算授权的模型，生成一个 `JSON → JSON` 受限工具。保存生成来源、候选源码、hash 与构建尝试，不能用预置代码替身冒充。
4. 可信执行器真实运行候选代码：无宿主访问、无网络、无安装、有限输入输出、强制时间与内存预算。语法检查或“禁止 import”只是预筛，不是隔离证明。
5. 独立验证器跑固定/留出/反例测试。允许在同一总预算内有限修复；每次新源码新 hash。资格通过后只允许在原任务和对应授权内试用。
6. 固定该版本处理本次输入；对来源引用、记录覆盖、稳定 ID 配对和差异做任务验收，输出遗漏/冲突/未知，而非静默丢弃。
7. 通过新增的窄业务命令保存私人分析报告，关联输入版本、工具版本、验证回执；保存失败显示产物已生成但未可靠保存。报告不写入共享岗位索引，也不改技能/简历/计划。
8. 将通过资格与本次结果验收的版本登记为可复用能力。能力包只保留实现、契约、用法、通用合成测试及验证元数据，个人报告仍在职业工作台自己的私有记录中。

### 5.3 第二遍：证明复用的是能力

换一批同格式、不同内容的合成输入：选择相同 capability/version/codeHash；**本次能力构建调用数为0**，但有新 inputHash、新运行和新结果回执。结果必须随新输入正确变化且只引用本次授权输入，不能来自第一份报告缓存；两批合法重叠内容可以重复出现，仅首轮存在且本轮未授权的唯一标记不得泄漏。必要的业务分析模型调用与“生成工具”调用分开统计。

再给一份超出适用格式的输入：停止误用，提出兼容的新版本候选或请求资料修正；旧版本和旧结果保留。不得为保持“复用率”强行套用不匹配工具。

### 5.4 首版不留白的前置

现有 CLI sandbox/练习 Worker 不作为通用安全运行器的完成证明。先以技术验证选定能实际限制资源及宿主访问的执行档位，满足附录 A05 后才接真实生成代码；做不到则不能宣称 MVP 通过。约束的是首版工具类型，不把“创建能力”无限后置。

## 6. 在现有代码上的落位

保持现有 Host/Web 与领域实现，不先拆微服务。下面是建议职责分组；解析、构建、策略和验证可在内部拆分，不让调用方学习十几套平级接口。

| Module / Interface | 复用与新增职责 | 建议代码落点 |
| --- | --- | --- |
| CareerTaskCoordinator：创建/执行/取消/恢复任务 | 复用统一 Agent 历史与事件；新增八步状态、任务约定、固定输入版本、预算、checkpoint及真正执行/结果验证的区别 | `apps/agent-host/src/capabilities/` 新任务模块；现有 Web kernel 作 UI/历史 Adapter，不能把其三分钟页面请求当长期执行器 |
| CapabilityCatalog：评估/查询版本/登记验证/发布或停用 | 复用 ToolDefinition schema/effect 形状；新增 owner 范围能力目录、适用性、不可变制品、验证与失效记录 | Host 新私有能力存储；`packages/agent-contracts/src/` 增量契约；现有 OwnedStore 仅有 continuity/growth，需单独支持，不能伪称已存在 |
| CapabilityExecution：补齐/资格验证/执行固定版本 | 内部以不可自修改的策略和 Verifier 管理生成器、安装/服务 Adapter 与 SandboxRunner；可信宿主包装成 ToolDefinition，execute 只调用隔离运行器 | 先放 Host 内；复用现有 ToolRegistry 的预算/取消/幂等思路，但不把动态源码 import/eval 到 Host 或 Web 主上下文 |
| WorkspaceGateway：读快照/提交明确领域命令/查询回执 | 复用现有简历采用/历史保护、机会库真实状态、成长计划采纳；新增私人分析报告命令。授权、schema、预期版本、幂等、回执集中执行 | 先为首个报告写入口建立实现；浏览器拥有的简历写入经当前有效会话 Adapter 调用原持久化，不假设 Host 已拥有浏览器库 |

Workspace 的查询和提交是两类权限。可选命令名称如 `saveJobComparisonReport`、`proposeResumeChange`、`acceptResumeProposal`、`adoptLearningPlan`、`recordConfirmedApplication`，都是建议，不是当前可调用工具。使用原子版本检查及持久回执；不提供万能路径写入命令。

当前 ToolRegistry 的回执 Map 不是跨进程事务，浏览器私人机会库读后写也不是多进程 CAS。首版限定单 Host 权威写入者，补原子提交和持久回执；多实例部署另验。当前 tool-adapter 的 threadId scope 不可当鉴权，新路径由已认证 principal 注入。原生 CLI 账号模式禁用继续保留。

## 7. 用户体验：让能力补齐服务任务，不制造配置中心

仍从统一 Agent 或具体业务页面发起。任务卡默认只显示：正在完成什么、当前阶段、产物/来源、需要用户决定的一件事、暂停/取消。详细技术信息按需展开，不常驻挤占输入框。

真实阶段示例：“核对输入与能力 → 缺少该格式的读取能力 → 正在构建 → 正在验证 → 正在比较 → 报告待核对/已保存”。不是每步固定动画，没有证据不显示虚构百分比。

需要扩大权限时，明确展示新增动作、涉及资料/目的地、费用上限/有效期以及拒绝后的可用路径。在既有有限授权内的低风险步骤连续执行；保存个人事实、发送材料等沿用业务确认。

完成卡显示本次结果、验证范围、未解决项，以及“新增/复用了哪个能力版本”。能力详情作为任务的次级入口：用途、来源、适用输入、验证日期与局限、当前权限、历史版本、停用。首版不建设公共 Skill 商店、排行榜或大型设置页。

## 8. 实施里程碑与退出条件

以下为建议顺序，不是本轮代码施工承诺；M0/M1与此前已完成的写作UI P0是不同批次。

| 阶段 | 本批交付 | 退出条件 |
| --- | --- | --- |
| M0：可信接口与受限执行器 | 首个业务任务约定、报告写入口、私有制品/回执、执行器资格技术验证 | 附录A01/A05/A08/A09可执行验收通过；不能仅以接口/mock完成宣称能力闭环完成 |
| M1：首个完整八步 MVP | JD新格式工具真实生成、资格测试、首次业务报告、能力沉淀与第二次复用；同批完成故障/撤权/并发回归 | A01–A09、A11–A12全部通过；真实生成与确定性回归分开报告；三个实物可核对，真实用户数据不参与 |
| M2：第二条业务复用 | 以项目证据整理或另一种岗位输入检验通用性，复用生命周期；组合已有能力，输出贡献待核实项/简历提案 | 不复制一套运行管理器；业务结果走原版本/事实规则；无本人确认不转成个人贡献 |
| M3：安装与外部服务档位 | 先选一个有真实需求的受控依赖或服务，如实践运行器或语音；逐项落实供应链、数据/费用授权 | A10逐适配器通过，旧版本可保留，失效不偷偷换提供方，不默认开外部投递 |
| M4：长期职业任务 | 目标关联多任务、依赖/调度、持久任务授权、重启恢复和通知，支持暂停/到期 | 浏览器关闭语义、Host重启、授权到期、费用/次数上限、回执恢复均实测；不把持续记录称为后台自治 |

每阶段使用源码契约/合成回归先验证，再做本人授权的真实生成或外部协议验收；两种证据分开。不会用模型替身证明真实生成，也不会用一次真实模型成功替代边界回归。

## 9. 评价指标和范围控制

- 业务任务验收通过率、待核对/部分完成/失败的原因；不以聊天完成或工具exit 0计成功。
- 合格能力命中后的构建调用数、新输入上的实际复用比例、是否减少同类任务重复构建；不追求无条件高复用。
- 首次与后续的耗时/费用实测，区分构建、执行、业务模型分析成本；不承诺预设提速比例。
- 越权、跨账号/跨任务授权混用和重复业务效果必须为零；错误拦截和来源不确定不算“失败要绕过”。
- 新能力适用范围、失效/停用记录、被影响的历史产物可定位；版本回滚不修改用户历史资产。

下一轮若进入实现，应把 M0＋M1 作为第一项完整能力产品交付，先核对运行器方案和明确的模型调用预算。仅交付目录/对话提示不算完成；本轮仍停在规划，无模型调用、工具安装、真实数据迁移或新后台任务。
