# 总调度与两个执行 Agent 的分工方案

日期：2026-10-19。状态：**供讨论的实施方案，尚未启动开发或决定接入**。承接 [career-ops 复用评估](../research/career-ops-comparison-2026-10-19.md)，保留当前非 Agent 工作台优先与岗位地图工程目标。

这里的三个角色是开发协作分工；产品内的自主 Agent 层仍按既有顺序后置。

2026-10-19 补充：用户已澄清实际问题是“产品接入 Agent 做什么比较好”。本文保留为开发协作历史提案，不代表已接受的产品 Agent 架构；最新产品建议见 [产品内 Agent 场景与边界](product-agent-scope-2026-10-19.md)。

## 第一批目标

总调度先处理现有四平台执行端运行接线，两个执行 Agent 在统一基线上并行补充：

1. 一个有实际关注公司样本的官网来源适配器，首选飞书招聘；Mokahr 为后续候选。
2. 可持久保存、可核对的人工 JD 收件箱，确认后接既有 JD 分析或私人机会预填。

统一规范索引的人工导入、完整证据匹配报告及事实检查增强分别立后续批次，不把首批私人机会接续描述为地图入库闭环。书签直传如尚无可靠配对/接收契约，先提供复制/JSON导入路径并明确剩余工作。

## 角色与职责

| 角色 | 主责 | 交付 |
| --- | --- | --- |
| 总调度 | 范围、共同基线、共享协议、现有运行修复、入口接线、集成与发布验收 | 可运行共同基线；契约和写入边界；共享文件改动；实际运行证据；整体验收与续聊记录 |
| Agent 1：官网来源 | 按现有 SourceAdapter 实现飞书招聘的有限读取、归一和证据 | 独立适配器、协议契约、禁用配置建议、许可归属、定向测试和有限实站记录 |
| Agent 2：人工 JD 收件箱 | 原文输入、持久草稿、字段核对、重复提示与确认采用 | 独立 UI/纯逻辑/存储模块、导入格式、定向测试和浏览器验收；通过 callback 接现有 JD/机会流程 |

两个执行 Agent 向总调度交付具体变更与证据，总调度统一维护主入口、主分支和发布。任务有依赖或需要修改共享文件时，先给总调度接口变更建议，避免各自改不同版本。

## 总调度先冻结的事项

- 当前工作区有大量未提交功能，先核实改动归属和稳定停点，形成可恢复、经核对的共同源码基线；执行分支均从该基线建立，不能直接从旧 main 取到缺依赖版本。私人数据、Key、SQLite、profile 和临时证据保持既有忽略边界。
- 现有 `SourceTransport.request` 明确为 **GET-only**；飞书招聘与 Mokahr 读取列表需要 POST。由总调度设计并验证受控查询 POST 能力，约束可信适配器、固定来源端点、请求体/方法、字节/次数/超时/取消/限流，以及重定向和 DNS。不能让子 Agent 临时绕过 transport 直接 fetch。
- 冻结来源记录/分页/覆盖的输入输出，保持 `sourcePublished*` 与 `sourceUpdated*` 分离；截断和摘要标明完整性，地点不自动得到坐标。
- 冻结收件箱草稿契约：原 URL、捕获方式、接收时间、原文、候选字段、校验问题、处理状态及稳定 ID。采集时间不充当发布时间；原文不可被编辑字段覆盖。
- 冻结 Agent 2 的确认采用 callback，明确接续 JD 核对/分析或私人机会预填。收件箱草稿不自动进入公共岗位快照，候选公司/坐标/薪资不自动升格为核实事实。
- 共享服务启停、现有 SQLite 备份、真实索引写入和浏览器 profile 归属操作统一由总调度执行。

## 文件所有权

拟使用独立 worktree/分支实施，例如 `codex/atlas-feishu-source` 与 `codex/jd-capture-inbox`；实际创建属于下一步实施，不在本轮完成。

| 范围 | 唯一修改者 |
| --- | --- |
| 现有 transport/公共契约、包 exports、registry/application 注册、配置汇总 | 总调度；Agent 1 提交所需接入清单 |
| `apps/web/vite.config.ts`、现有会话路由与运行接线、`App.tsx`、`AtlasWorkspace.tsx`、现有机会入口 | 总调度；执行 Agent 以 callback/独立组件交付 |
| 新官网适配器及其独立契约/测试、来源实现文档、第三方许可单元 | Agent 1 |
| 新收件箱组件/导入与校验纯逻辑/独立存储模块/测试 | Agent 2；新增路径在契约冻结时确定 |
| `package.json`、锁文件、公共 barrel、全局样式和翻译汇总 | 总调度；新增依赖须说明用途 |
| `activeContext.md`、`progress.md`、决策/路线图/公开交付报告 | 总调度；执行 Agent 仅回报应更新内容 |

共享入口改动由总调度集成，不让两个分支分别混入已有并行成果。各 Agent 只暂存/提交自身任务文件，提交前检查暂存差异。

## Agent 1 的验收

- 先实现单来源的小闭环：配置识别 → 有限读取 → 原始岗位身份及链接 → 职责/要求/地点证据 → preview → 手动 sync → 同一索引查询。
- 复用既有 SourcePage/SourceJobRecord 和 transport；限制页数、记录数与详情请求，正确区分空结果、失败、受限和部分覆盖。游标绑定来源、配置与查询，重复读取保留更新观察。
- 有效时间与单位须按来源含义保存；无依据字段保持未知。实际描述截断不能标为完整详情。
- 定向测试覆盖字段、分页、重复身份、损坏响应、取消、超时、限流及预算；网络测试使用受控输入，真实请求另列数量和范围。
- 在不修改用户原库的独立临时服务/数据目录完成有限实际样本；共享私有索引的最终同步由总调度验收。
- 交付固定来源/许可、文件清单、验证命令与结果、实站限制，以及总调度要完成的注册改动。作者历史实测和合成测试不算本轮实站结果。

## Agent 2 的验收

- 输入首先支持粘贴或明确格式的 JSON 导入，保存原文与原 URL；书签可先生成复制/下载结果。如本批加入直接发送，需先由总调度冻结配对、Origin/Host、输入限制、幂等和存储路径契约，不能把长期 service token 放进外部页面。
- 明确区分待核对、已采用、暂缓与丢弃；暂缓不被强制清空。确认前可纠正候选字段，原文仍可回查。
- 草稿持久化并能刷新恢复；输入无效、重复捕获、容量/存储失败有可理解反馈。重复 URL 不等于正文未变化，不静默覆盖旧内容。
- 用户显式确认后，接既有 JD 核对/分析或机会表单；接续后仍按原表单保存流程，不假装已写规范岗位索引/地图。删除收件箱项不删除已采用的私人记录。
- UI 样式复用现有工作台。专项检查原文展示、窄屏、键盘、刷新恢复、错误提示和既有 JD/机会回归。
- 不操作真实简历/Fact，不自动生成个人经历、薪资、坐标或发布时间；外部数据作为数据处理。

## 调度与集成顺序

1. 总调度核对基线、修开发宿主加载与新接口，冻结两组契约；两个 Agent 可先准备各自独立解析/交互逻辑。
2. 两条执行分支并行。按可验收小段交付，每次说明已完成、证据、剩余限制和共享接入需求；阻塞必须带具体错误/最小复现。
3. 总调度先接来源注册并验 preview/sync，再接收件箱 callback 和工作台入口；按依赖集成，解决版本与共享文件冲突。
4. 执行 Agent 完成各自定向检查，总调度对合并后的同一源码快照完成全量测试、lint、types/build，以及对应真实网页与来源验收。静态 Pages/Docker 与本机执行宿主分别说明边界。
5. 按功能提交和发布验收，更新报告、路线图和续聊记录。真实平台门禁、未完成规范入库或其余地图目标保留为未完成，不以单个来源成功替代整个目标。

第二批再安排“JD 要求/Fact 证据报告”和“生成材料事实检查”，仍可沿用总调度统一协议、两个 Agent 各自独立模块的组织方式。
