# BetterMe 桌面 JD 助手与可视化 Agent 工作流

日期：2026-11-05。状态：可行性研究与设计，不是已发布功能或自动执行授权。[移动双入口设计、实施与验收](#mobile-job-workflow)已同步至根 README；未接入设备、安装 MCP／OCR、运行模型、操作招聘账号、采集真实 JD、发送材料或更改 Docker。本文不改变现有产品版本范围。

## 1. 建议结论

电脑端路线值得做，但产品应是**可观察、可暂停、可核实的求职执行工作流**，而不是一组截图坐标脚本。

- 先做用户指定页面／窗口的只读 JD 获取，再接材料准备和预填；发送单独立项、单独授权。
- 浏览器 DOM／无障碍树优先，OCR 提取文字，OpenCV 补足视觉锚点／帧差；识别器和执行器分开。
- 使用已有 Agent Host、JD graph、事件和业务行动卡；先增加工作流运行视图，不立即引入另一套 n8n／Dify 运行系统。
- 本地 Ollama 做结构化、匹配和计划候选；权限、材料版本、暂停和外部副作用校验由确定性代码掌握。
- Career Workspace 继续拥有岗位、简历、投递与回执。图只是 Run 的展示，不是第二套业务数据库。

外部技术证据及局限见[官方资料研究](../research/desktop-vision-automation-primary-sources-2026-11-05.md)。本报告没有证明 OpenCV、真机或桌面端能降低账号封禁风险；用户许可、系统权限和平台许可是三件不同的事。

## 2. 可行性分级与技术分工

| 场景 | 技术判断 | 首轮边界 |
| --- | --- | --- |
| 用户选定网页上的 JD 读取 | 高可行性，但仍取决于页面结构和许可 | 有来源、时间、完整性与缺失标记；不跨账号或突破访问限制 |
| 授权窗口／图片中的 JD OCR | 可行，需要招聘截图专项测试 | 不能把当前一屏当完整 JD，不猜缺失薪资或招聘人 |
| 匹配、草拟沟通文案、生成材料候选 | 适合本地模型 | 仅使用本人已确认事实；候选不能直接成为简历版本 |
| 自动预填平台表单 | 有条件可行 | 保存／上传也可能有副作用，逐项定义权限；不把“预填”统称只读 |
| 最终沟通、共享简历、提交申请 | 技术可实现部分流程，实际许可与稳定性未验证 | 独立动作、逐次批准、执行前复核、结果未知禁止自动重试 |
| 三平台长期无人值守批量投递 | 不能据现有证据承诺 | 不作为首期验收目标，不提供防封承诺或规避检测机制 |

推荐的感知顺序是 `语义读取 → OCR / OpenCV 视觉补足 → 人工确认或导入`，不是每个页面都要完整跑三遍。浏览器优先 DOM／浏览器无障碍树；原生应用优先操作系统无障碍接口，而不是先 OCR 失败再用原生控件语义。截图由受控宿主捕获接口取得，OpenCV 处理图像，不能把图像库当成跨平台窗口截图／授权 API。Playwright MCP 默认提供结构化无障碍快照，并支持视觉模式；它并不提供安全隔离边界。[Playwright MCP](https://github.com/microsoft/playwright-mcp)、[Vision Mode](https://playwright.dev/mcp/vision-mode)

复制文本、粘贴 URL 和上传明确授权的截图始终是独立可用入口，不要求用户先安装桌面执行器；人工导入仍需来源和完整性标记，不等于内容已核实。

OpenCV 处理像素相似度、候选区域与变化检测；OCR 读文字；平台适配器解释当前页面；执行器通过浏览器或原生输入 API 执行。模型提出的坐标不是可信目标。旧截图、缩放、跨屏、滚动、弹窗或用户接管均应触发重新观察。[OpenCV 模板匹配](https://docs.opencv.org/4.13.0/d4/dc6/tutorial_py_template_matching.html)

### 国内平台适配不能只换图标

沿用[现有国内行动卡](../domestic-delivery.md)的三类动作：发起沟通、共享简历、提交申请，分别准备、批准和记录。

- BOSS：页面显示“沟通”不能直接解释为已投递；明确是发招呼、发附件还是共享平台在线简历。
- 51job：预览实际选择的默认／在线简历与附件，不能只检查 BetterMe 的 PDF。
- 猎聘：平台入口、当前招聘主体、岗位和动作结果分别核对；不假定按钮和 BOSS 相同。
- 每个适配器声明“支持哪些客户端版本／页面／动作、如何识别当前状态、如何验证结果”。未支持页面交还本人，不靠模型临场猜按钮。

这些是契约与测试要求，不是已完成三平台联调。既有协议调查日期为 2026-11-04，具体客户端最新适用条款与真实操作许可仍需再次核验。

### 增量建议：Platform Policy Registry（平台策略登记）

把平台规则从提示词中的提醒变成执行前可查询的策略记录。按“平台＋客户端／渠道＋具体动作”登记，而不是给整个平台贴一个永久的“支持自动化”标签。读取、上传、预填、沟通、共享和提交分别判断。

建议记录策略来源 URL、适用版本／日期、人工复核者与时间、复核期限、允许／禁止／未知、授权合作范围及手动替代路径。该记录是工程决策依据，不是法律许可证明，也不由 Agent 自行改为允许。规则未知、过期或冲突时关闭对应自动动作，并提供人工导入／手动交接；不试图借 OCR 绕开原来的限制。

执行条件取交集：**平台许可范围 ∩ 用户本次授权 ∩ 当前工具已验证能力 ∩ 当前系统权限**。满足其中一项不推导其他项成立。比如允许读取 JD 不等于允许上传简历；用户批准也不能覆盖未知的平台限制。这是待实现设计，不给三家平台预填“已允许”。

## 3. Agent 应在什么时候问用户

不做一张首次使用必须填满的巨型表单。把问题绑定到阻塞它的节点，能读取已经明确授权、确认且未过期的资料就复用；未知值保持未知。

| 信息类别 | 例子 | 何时索取／失效 |
| --- | --- | --- |
| 职业目标 | 岗位方向、城市、薪资区间与税前／月薪口径、远程偏好、排除公司、硬软条件 | 检索和匹配前；目标改变后相关分析标旧 |
| 职业事实 | 已确认经历、技能证据、可分享联系方式、简历版本 | 准备材料前；修改后重新生成差异，不能继承旧批准 |
| 本次范围 | 平台、查询词、选定窗口、页数／时长预算、截图留存范围 | 读取前；只读授权不允许保存到平台或上传 |
| 环境条件 | 已登录账号标记、窗口选择、屏幕／辅助功能权限、连接状态 | 实际工具需要时；密码、Cookie、验证码不进入模型或普通表单 |
| 发送批准 | 精确岗位、接收对象、动作、消息、在线与附件简历版本、分享范围 | 每个外发动作前；变更、过期、切号或撤权立即失效 |
| 结果核实 | 平台回执、可验证的记录或本人核实说明 | 动作后；工具 exit 0、按钮消失和没回复都不是成功证明 |

示例：用户输入“找上海全栈工作”，读取节点可继续准备查询，但匹配节点提示“最低薪资尚未确认：填写／本轮暂不筛选”。这个选择应保存到本轮目标版本，而不是让模型猜 20K。发送节点再展示收件对象和材料版本，不提前把资料问题包装成发送授权。

把 `missing_information`、`missing_permission`、`capability_gap`、`environment_unavailable`、`uncertain_outcome` 分开：问更多资料解决不了权限缺失；安装新工具解决不了平台不允许；结果未知更不能通过重试自动“修好”。

### 增量建议：Agent Preflight（执行前检查）

每个阶段开始前生成一份版本化检查结果：已满足条件、缺失字段、过期／冲突事实、缺少权限、策略阻断、环境问题和下一步。只读取当前任务已授权的档案范围，不因“检查完整度”扫描全部私人资料。动态表单只收当前必要信息，并解释为什么需要、是否可跳过以及影响哪一步；“已填 6/8 项”只是填写进度，不是事实可信度或任务成功率。

资料层复用 Career Workspace 现有 Fact 与证据，不新建 Agent 专属 Candidate Fact Store。重要字段应有来源、确认主体／时间、版本、适用范围与冲突／过期状态；本人确认不等于独立核实，不使用一个 `verified: true` 混淆二者。参考文本中的 C# 年限、20K、城市和到岗时间仅是示例，不写入用户求职事实。

## 4. 可视化产品：先做运行视图，再考虑自由编排

默认用户提出目标，Agent 生成受约束的计划；用户看懂、补信息、批准关键动作，不需要自己拖线。高级模式将来可以编辑规则／模板，但运行中的定义必须冻结，修改产生新版本。

### 界面结构

1. **任务头部**：目标、平台和资料范围、运行预算、当前状态、暂停／接管／取消。
2. **主工作流图**：节点显示等待、执行、补资料、审批、阻塞、完成；多个岗位作为可展开子流程，而不是一次铺开几百个节点。
3. **当前操作卡**：缺资料时就地出现表单；待批准时出现材料差异、接收对象和明确动作；不要求用户翻聊天记录找按钮。
4. **节点详情**：输入版本、证据、简短决策依据、脱敏工具名／参数、输出、时长、错误、后续动作。
5. **业务结果区**：候选岗位、材料版本、待核实结果和已保存回执；不以节点变绿替代业务接纳。

主链路：目标确认 → 按需补资料 → 读取授权 → 获取／结构化 JD → 匹配与证据检查 → 准备材料 → 逐次批准 → 执行前复核 → 工具操作 → 核验 → Workspace 回执。信息不足时等待；权限或环境改变时暂停；未知结果进入人工核实，不回到发送节点自动重试。

### “思考、推理”展示成可核对的决策摘要

例如：“该岗位薪资未公开，所以没有按薪资筛除；技术要求与两条已确认项目证据相关；城市满足硬约束，出差频率仍待核实。”显示依据、假设与待核实项，而不是原始内部思维链或模型自由输出的长推理文本。

`agent.thinking` 只代表处理阶段，不能当作可验证的动作或结果。工具调用由运行时事件证明；输入来自谁、证据是哪一版、为何暂停，应可点击查看。

### 状态、恢复与真实执行

建议节点状态：`pending / running / waiting_input / waiting_approval / blocked / succeeded / failed / skipped / cancelled / outcome_unknown`。`skipped` 应保存条件和原因，不能显示成成功。这不是要求立即替换所有现有 Run 状态；先通过版本化节点投影适配旧消费者。

事件补充 `workflowVersion / nodeId / attempt / inputVersion / effect / artifactRefs`，保留已有 `runId / sequence / timestamp`。状态从已验证事件与持久化检查点重建；页面重开不是重新执行。缺字段表单包含稳定的 requestId、schema、来源、有效期与预期版本，提交时服务端重新检查 owner／会话代次。

有副作用节点先持久化 intent 和 attempt，再执行；批准绑定内容摘要并一次性消费。平台无幂等接口时，不能承诺 exactly-once。发送后进程退出／网络超时：标记未知，重启后先查证，不自动补点。停止只能阻止后续动作，不能撤回已经发出的简历。

### 增量建议：受约束的动态路由，而非任意改图

Agent 可以在已定义、已验证且当前获准的路径之间选择：DOM 不完整→视觉补足；识别存疑→本人核对；缺资料→表单；平台策略不允许→手动交接。切换方法不扩张权限，也不能把被平台禁止的读取改用截图继续做。低匹配只能按用户确认的硬条件或可解释规则跳过，不因未经校准的模型总分静默丢岗位。

运行保存计划版本与每次路由决定、原因和证据；重规划产生新版本并保留历史。输入修改后只使依赖它的分析／材料和批准失效，展示受影响节点；不从头无差别重跑，更不重放已发送动作。节点重试须区分无副作用读取、需重新批准的写入和未知外部结果。

节点详情中的 Execution Trace 复用真实事件，按需展开截图证据、尝试次数、耗时、模型和工具版本。Token／费用只有提供方实际返回或有可靠计算依据时才显示，未获得就标未知，不制造精确数字。默认模式不放完整节点工具箱；自由编排与运行观察是不同产品阶段。

## 5. n8n、Dify、React Flow 各处在哪一层

| 方案 | 适合 BetterMe 的部分 | 不应混淆的边界 |
| --- | --- | --- |
| React Flow + 现有 Host | 产品内节点图、交互表单、运行详情；优先评估 | 图形组件不是调度器、事务或权限系统 |
| n8n | 外部通知、日历、邮箱等集成；复杂组织流程的可选独立编排 | 不让它成为第二份职业业务权威；内嵌／商业交付另做许可审查 |
| Dify | LLM 应用／RAG 原型、表单暂停和分支交互的参考 | 不自动获得用户桌面权限；另有用户、凭据、数据存储与部署成本 |
| MCP | 接工具和补资料交互的协议 | 不是节点画布、业务审批系统或任务数据库 |

React Flow 是可定制的 MIT 许可节点 UI 库；n8n 官方支持在指定工具执行前暂停审批；Dify 官方 Human Input 节点支持表单、决策分支与超时处理。这些足以证明所需交互模式可以实现，但不代表 BetterMe 已接通它们。[React Flow](https://reactflow.dev/)、[n8n 人工审核](https://docs.n8n.io/build/integrate-ai/ai-examples/human-in-the-loop-for-tools.md)、[Dify Human Input](https://docs.dify.ai/en/cloud/use-dify/nodes/human-input)

n8n 的代码许可并非简单等同 MIT；若将其嵌入对外提供的产品，应针对实际交付方式核对许可，不在本次研究中做授权结论。[n8n LICENSE](https://github.com/n8n-io/n8n/blob/master/LICENSE.md)

## 6. 小红书文章中 10 个 MCP 的取舍

已通过公开网页读取用户提供文章《别看 Star，看装机：下载最多的 10 个 MCP》（小鱼玩AI）的正文名单。正文称统计 2026 年 3–9 月 npm／PyPI 下载，且提示下载不等于独立用户。本轮没有重算包级统计、检查全部配图或核实独立安装数，不把排名当作选型依据。[原分享](https://xhslink.cn/o/2S9Qexhrd9n)

下表是按项目官方来源评估；名称相同不保证是同一个包，真正接入前必须核对 registry 标识、维护者、版本和所需权限。

| MCP | 建议 | BetterMe 用途与限制 | 官方来源 |
| --- | --- | --- | --- |
| Playwright MCP | 产品侧优先评估 | 允许访问的浏览器语义读取／受控操作；不开放任意点击、脚本与文件给求职 Agent | [Microsoft](https://github.com/microsoft/playwright-mcp) |
| Chrome DevTools MCP | 开发侧优先 | 排查网络、控制台、性能、UI；有浏览器操作能力但不与 Playwright 重复承担同一执行角色 | [ChromeDevTools](https://github.com/ChromeDevTools/chrome-devtools-mcp) |
| Storybook MCP | 条件接入 | 有组件 stories 后辅助组件理解和测试；不是 JD／投递工具，本轮未发现根和 Web package 声明 Storybook | [Storybook](https://storybook.js.org/docs/ai/mcp) |
| Context7 | 开发侧优先 | 查依赖版本文档与代码例子；不是招聘数据源，不传私人简历 | [Upstash](https://github.com/upstash/context7) |
| Filesystem | 有限场景，后置 | 指定导出／截图目录；优先复用现有业务文件入口，不开放整个用户目录或让它绕过版本保存 | [官方参考实现](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem) |
| Fetch | 产品侧可选 | 公开且许可访问的静态文本／公司官网；不能替代浏览器登录、动态 UI 或验证码处理 | [官方参考实现](https://github.com/modelcontextprotocol/servers/tree/main/src/fetch) |
| Time | 暂不需要 | 时区与时间计算用普通业务函数即可，没必要多部署一个服务 | [官方列表](https://github.com/modelcontextprotocol/servers) |
| Notion | 本人确有需求再接 | 经明确授权导出学习计划／求职记录；不自动同步整份简历，不替换 Workspace | [Notion](https://developers.notion.com/guides/mcp/overview) |
| Everything | 仅协议测试 | 这里按 MCP 官方参考服务解读；它是客户端测试示例，不是万能业务服务，也不是 Windows Everything 文件搜索软件 | [官方 Everything](https://github.com/modelcontextprotocol/servers/tree/main/src/everything) |

## 8. 本地 Ollama、Docker 与通知

建议部署：Web／Agent Host／数据库和可选 OCR worker 可容器化；Ollama 按现有本地部署使用；实际桌面捕获与控制由宿主 companion 承担。Docker Desktop 的 Linux VM 与宿主 GUI 不是同一个交互会话；给容器一个 host 地址并不会获得窗口控制权。[Docker Desktop](https://docs.docker.com/desktop/features/networking/)

Companion 主动配对、限定 owner／工作区／窗口、短期凭据、精确工具清单、可撤销；不挂整个 home、浏览器 profile、Docker socket，不要求 privileged。截图只保留任务所需区域，独立保留期，不进入公共岗位索引。

Ollama 工具调用由应用实际执行，JSON Schema 输出仍需业务校验；按所选模型验证能力，不把“支持 Ollama”当作所有模型都能规划、视觉识别和用工具的保证。[Tool Calling](https://docs.ollama.com/capabilities/tool-calling)、[Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)

通知仅订阅 `waiting_input / waiting_approval / outcome_unknown / completed` 等有意义事件，去重、最小化内容并指向重新鉴权的任务页；不在推送里包含完整 JD、联系方式或简历，不把通知链接当发送许可。先站内待办，再按明确需求接本地通知／Web Push／外部服务；本轮不新建定时任务或修改推送配置。

MCP 可承接补信息交互，但不是业务批准。当前官方 latest 为 2026-07-28，相关多轮请求与旧版握手有差异，详见研究文档第 5 节；选定 SDK／server 必须做协议版本匹配和恢复测试，不能把 `input_required` 的继续请求当成重新发送简历。

## 9. 推荐实施顺序与验收门槛

1. **运行视图纵切片**：将现有 JD 分析流程接入节点图与缺字段卡；模型不增加桌面权限。验证刷新恢复、拒绝、取消、过期、切号及迟到事件。
2. **只读桌面 JD 助手**：用合成／明确授权脱敏页面，DOM 主路径，PaddleOCR＋OpenCV fallback。验证多 DPI／主题、滚动缺段、重复岗位、来源绑定；记录字段正确率、完整性、延迟和内存，不预设虚构准确率。
3. **模拟材料准备与预填**：固定材料版本，在本地模拟页面预填，不外发；覆盖材料变更、错窗口、陈旧截图、权限撤回和用户接管。
4. **模拟发送故障**：测试可能已发送但超时／断网／重启；未知结果不重发，批准不能跨动作复用。所有恢复分支有持久化证据。
5. **具体平台试点**：另行核验当前许可，取得明确账号／资料／操作授权，只选一种动作和一种客户端；没有这些条件就保持手动交接。

首个里程碑是“用户能理解并接管的一条真实只读闭环”，不是“装了十个 MCP”或“画出了十个绿节点”。自动采集／投递效果、本机性能、平台许可、通知送达及 Docker companion 连通均未在本轮验收。

参考对话的 Job Intelligence、运行视图、Desktop Companion、Application Agent、能力生态可作为工作包，而非强制五阶段瀑布。先将现有 JD 分析、按需输入与真实事件接成一条可观察闭环，再扩展读取方式和动作。能力判断／补齐／验证／复用贯穿各工作包，不能退回“最后才研究能力闭环”；已有 M0/M1/M2 受控成果也不因新的路线图被重算为尚未开始。

## 11. 长期增量：统一 Agent 的双循环与 BetterMe MCP 出口

参考对话把 Career Agent 和 Capability Agent 分开，值得吸收的是**两种职责和闭环**，不是默认创建两个平级聊天入口、两套运行时或两份职业记忆：

- 业务循环：理解职业目标 → 获取／分析 → 材料提案 → 本人批准 → 业务执行／接纳 → 核验回执。
- 能力循环：确有能力缺口 → 复用／组合／接入／构建方案 → 独立测试 → 人工批准所需权限及晋级 → 版本化复用。

统一 Personal Career Agent 调度两者。资料缺失、政策禁止和授权缺失不能伪装成“能力缺口”；生成 Adapter 不能自动安装、获得浏览器会话或发送权限。借鉴“打开→观察→行动→核验→释放资源”的生命周期，但只释放本任务创建的会话／资源，不关闭用户原有标签或丢弃未保存内容。

BetterMe 将来不只消费 MCP，也可提供受控的职业能力出口。以下是候选契约，不是已存在 API：

| 接口类别 | 示例候选 | 设计约束 |
| --- | --- | --- |
| 只读查询 | `search_jobs`、`get_job_detail`、`get_resume_versions`、`get_application_status` | 服务端推导 owner、最小字段、分页与范围授权；列表不能顺带泄露完整简历 |
| 已授权分析 | `analyze_job_match`、选择性 `get_candidate_profile` | 绑定具体资产／字段／版本，联系人与私人内容默认不返回，模型处理范围单独检查 |
| 准备提案 | `create_resume_draft`、`prepare_application` | 返回候选／差异／审批引用，不直接采用简历或发送；可能的模型调用、写入和费用须声明 |
| 外部发送 | 首版不提供通用 `submit_application` | 后续若开放，另做平台许可、精确动作授权、幂等及未知结果处理，不继承外部客户端的口头批准 |

MCP Adapter 必须调用 Workspace 同一应用命令与校验，不直接操作数据库；外部客户端身份也不等于 BetterMe 用户身份，采用受众／作用域绑定和按账号授权，不能信任调用方传来的 owner。首先考虑受限只读出口，再考虑提案型写入，最后才讨论有外部副作用的能力。

## 13. 手机上的岗位如何进入同一个工作流

**第一版交付目标（待实现）：** 用户从 Android 测试页或 iPhone 分享菜单交给 BetterMe 一份 JD，能看清读到了什么、缺什么、为什么推荐，并得到可核对的行动卡草稿。终点是**草稿交给本人**，不是“已投递”。这里的“第一版”仅指移动入口，不重定义 BetterMe 的整体 V1。

**Android 第一版限隔离测试设备和模拟招聘页。** Mika 的任务参数没有硬性只读开关，默认询问模式不会为普通消息或表单逐次确认。即使目标写着“不要发送”、UI 没有发送节点，也管不住受托执行器在手机里的点击。测试环境须隔离真实账号、联系人和可外发服务；不能证明动作受限时，不在真实招聘账号上运行，改由本人提供允许使用的内容。Mika 的 `request_id`（如所选版本支持）仅去重委托任务；`done` 不是平台回执。[Mika 模式说明](https://github.com/wangzan101/Mika/blob/main/docs/modes.en.md) · [任务状态与恢复](https://github.com/wangzan101/Mika/blob/main/docs/mcp.en.md)

```text
Android · Mika 任务结果 ──┐
                         ├→ 待核对岗位卡 → 补信息／核对原文 → JD 匹配 → 材料候选 → 行动卡草稿 → 本人接管
iPhone · 主动分享内容 ───┘
```

“待核对岗位卡”是本次 Run 的输入，不等于已经收藏的岗位。两条路径使用同一份观察契约：**来源**（平台、入口、可得的岗位 ID／链接、获取时间），**内容**（岗位、公司、城市、薪资原文、要求），**证据**（每项对应的原文段落或已授权截图区域、完整性及缺失字段）。运行和证据绑定服务端认定的账号与工作区。无法确定岗位身份时保留临时来源标识；名称相似不自动合并，不覆盖已保存记录。证据最小化、可删除，不把整屏或分享链接中的凭据写入日志／公共岗位库。

可视化沿用第 4 节的 Run 事件，按节点显示**输入、实际调用、证据、决策摘要、等待原因和下一步**。例如：只分享了上半页截图 → 标记“部分 JD；薪资未知” → 让用户补图或显式选择“本轮不按薪资筛选” → 用已确认经历匹配 → 预览行动类型和材料版本。Android 节点展示 Mika 实际返回的任务状态，iOS 节点展示实际收到的内容类型；没有底层事件就不画逐次点击。补信息不等于批准发送，刷新不能重启任务；本人确认保存后，Career Workspace 才写入岗位／行动卡，Agent 不另建投递账本。

### 第一版怎么做（按可交付顺序）

1. **先通公共流程。** 在现有 React 运行视图设计和 Agent Host 的 JD graph 上，用固定合成 Job、目标和简历版本跑通“观察 → 补信息 → 匹配 → 草稿”。先定义节点事件、证据引用和等待／恢复行为；不先造拖拽编辑器、第二套图引擎或通用设备控制器。
2. **接两条薄入口。** iPhone 用分享菜单快捷指令提交选中的文字／链接／图片；Android 用宿主 Companion 与 USB Mika 委托隔离测试页的读取任务。两者都只产出上述观察，不分别实现匹配或简历逻辑。先用固定夹具验证规则，再用两部设备在隔离环境实际走各自的入口；分别记录版本与限制。
3. **接既有行动卡，停在交接。** 使用已确认事实准备草稿，预览 BOSS／51job／猎聘对应的“发起沟通、共享简历、岗位申请”之一。材料或目标变化使旧核对失效；首版不向平台预填、上传、发消息或提交，不调用三家真实账号验收。未来真平台试点须逐客户端／动作核对第 2 节的策略登记、明确用户授权和可执行的限制；平台许可未知就不执行。

<a id="mobile-acceptance"></a>

### 第一版怎么验收（以下均待执行）

统一夹具：同一虚构岗位 `DEMO-01`、一份已确认的合成简历、正文和缺薪资的局部截图；模拟页带“立即沟通”按钮，后台记录消息／上传／提交计数。每项保留脱敏 Run 事件、证据引用及 Workspace 写入结果；不使用真实简历、登录信息或平台账号。

| 场景 | 必须观察到的通过信号 |
| --- | --- |
| Android USB + Mika | 在隔离 Android 设备实际派单；任务 ID、终态与模拟岗位原文可关联。只有摘要或目标不明时停在补证据；不拿任意桌面截图冒充。模拟页三类外发计数始终为 0。 |
| iPhone 分享 | 在 iPhone 分享菜单分别交入文字、截图和只有登录链接的内容；三次均能找到对应 Run。截图能回看授权区域；链接不会变出正文。至少从一台非 Mac 电脑核对结果，全程不依赖镜像或 WDA。 |
| 两路汇合与缺字段 | 同一来源岗位的共有字段与夹具一致、证据各指向各自入口；局部内容保持“部分／未知”。补图或选择跳过薪资后，从等待节点继续一次；无稳定 ID 的同名不同岗不自动合并。 |
| 可视化、草稿和版本 | 刷新重建同一 Run，不重新派单。每个完成节点都有实际事件；修改岗位／材料后旧核对不可用；取消不生成新行动卡。用户确认草稿后可在 Workspace 查到对应岗位和材料版本，投递阶段不变。 |
| 断联、换号、撤权 | 断开 USB 或撤销配对后停止新的读取；换账号不能读旧证据、写旧草稿或接纳迟到回包。模拟“可能已发送但没有回执”进入“结果待核实”，恢复后外发计数不增加，不能凭 Mika 成功状态标为已投递。 |

**验收口径分三档：** 夹具通过只说明公共流程正确；某个真机入口通过才标记该入口“已连接”；两条入口和所有故障用例都通过，才标记移动首版闭环完成。即使全部通过，也不代表三家平台允许自动采集／投递、不会封号，或已获平台验证的投递回执。
