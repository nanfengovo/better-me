# 迈向更好 BetterMe：职业成长 Agent 产品规划草案

初稿：2026-10-16；当前优先级更新：2026-10-17。长期模块仍是规划，实施状态以最新交付报告为准。

## 最新实施顺序 · 2026-10-17

用户明确要求“Agent 层先不急，先把非 Agent 层做好”。当前先完成简历/导出与多简历、岗位发现/来源/筛选、手动投递记录与材料、跟进与备份，再扩国内官网、观察历史与真实地图。对话规划、契约学习、测评证据回流和自主执行后置，覆盖下文初稿中的旧优先级。

已实施机会库/列表/看板/同源统计、多简历与材料MD快照、GH/Lever/腾讯官网预览收藏、RenderCV YAML、DOCX、截止日/联系人/实际沟通、到期队列和16个开源资料入口。最新见[跟进与导出批次](../reports/non-agent-followups-and-export-2026-10-17.md)，前批见[工作区交付](../reports/non-agent-workspace-upgrade-2026-10-17.md)。地区分布仍为个人收藏库的文字统计；真实地图、跨源同岗、持续同步/观察历史、附件库和DOCX/PDF逐页视觉验收仍待推进。

补充四个用户指定来源的固定源码与许可核查见[Job Search项目对照](../research/job-search-comparisons-2026-10-17.md)；开源是方法与适配依据，链接入口不等于完整集成。

用户续轮要求先修复真实简历导入，并关注复杂截图及原稿布局/字号。当前质量批次见[真实简历导入修复](../reports/resume-import-repair-2026-10-17.md)：来源文本/OCR转录/待补录留档与结构化Fact分开；不同文件格式的原稿保真编辑、逐字段坐标证据和内容变更后的版面比较仍未实现，不能以六模板或格式校验替代。下一步应先验证这些导入边界，再扩大来源观察历史等功能。

## 1. 已确认的产品方向

BetterMe 是持续陪伴个人的职业成长 Agent：了解个人经历与偏好，观察目标岗位，找出值得解决的缺口，组织学习与练习，通过作品和测评验证改善，再把经过确认的成果用于简历、面试、投递和 Offer 决策。

用户本轮已明确：

- 第一服务对象是自己，技术岗社招，国内为主、兼顾海外探索。
- “强制学习”采用契约模式：提醒、专注计时、测验验收、补学和复盘，不采用系统锁机。
- 保留现有简历事实底座；原定下一阶段学习闭环，最新调整为先完善非 Agent 工作台。
- 初次规划先研究来源再编码；后续已按用户要求开展简历和非 Agent 工作区实现，以最新报告记录交付。
- 国内/海外是可切换的机会视图：地图、数量、列表和筛选结果同步变化，不预设用户已选择迁居或某种海外路径。
- 职位以公司招聘官网、LinkedIn、51job、BOSS、猎聘等原始发布平台为主要来源，开源聚合为补充；逐条展示来源、原文链接、时间与状态。
- 第一学习主线围绕现有工作经验和主技术栈，补目标 JD 中有依据的真实缺口；不默认切换成 AI/Agent 转型路线。

之前的“个人本地优先、好用后开源”“Headless Core + 多宿主”“同源事实、防编造”仍适用。扩大的是产品终局与路线图，不代表把所有远期功能同时纳入当前 V1。

国内/海外的具体地区、远程资格和个人申请条件留在可调整筛选中；当前无需先决定迁居路线。具体目标岗位、JD 和每周时间等在首次实际规划时澄清，不据此虚构个人技术能力或学习结论。

## 2. 成功标准与核心循环

核心循环：

`个人事实与偏好 → 目标岗位/JD → 可解释缺口 → 有限学习计划 → 学习/项目/测试/复述 → 可审查证据 → 用户确认的新事实 → 靶向简历/面试/投递 → 反馈与 Offer → 下一轮目标`

北极星指标建议采用“每周形成并通过验收、与目标岗位有关的能力证据”，辅以持续使用和求职转化；不把签到天数、聊天轮数、推荐链接数量、投递数量当作主要成果。

短期求职和长期提升是两个显式目标模式：紧急求职优先用既有能力优化材料与面试，长期提升才安排深入补课。不能让用户在达到某个虚构的完美能力分数前一直无法投递。

## 4. 产品模块及用户体验

建议主导航先按用户任务组织为“今天 / 成长 / 机会 / 求职”，持续对话入口贯穿四者。Offer、画像和配置先作为相关工作区内的页面，不一次铺十几个顶级菜单。

| 模块 | 输入 | 主要输出 | 先后 |
|---|---|---|---|
| 画像与事实 | 用户确认的经历、偏好、时间、约束、目标 | 有来源的履历和可编辑偏好，待核实信息 | 现有底座完善 |
| 职业对话 | 当前目标、事实、计划、近期反馈 | 可接受/拒绝/修改的目标和计划提案 | Agent 阶段后置 |
| 能力缺口 | 1–3 份选定真实 JD、已有证据、初测 | 有依据、有限且可行动的缺口列表 | Agent 阶段后置 |
| 计划与契约 | 每周时间、截止日、优先级、反馈习惯 | 滚动计划、今日任务、完成标准、补学/复盘 | Agent 阶段后置 |
| 学习资料与练习 | 具体缺口、基础、语言、预算 | 少量精确章节/练习、作品任务 | Agent 阶段精选接入 |
| 测评与刷题 | 能力目标、题目、评分规则、提交材料 | 可定位反馈、复测和证据 | Agent 阶段先做一种任务类型 |
| 模拟面试与口语 | 已确认真实故事、JD、目标语言 | 分轮追问、口语反馈、补练计划 | 先文字，后语音 |
| 简历与模板 | 已确认 Fact、目标 JD、输出场景 | 多版本简历、修改差异与来源、可解析导出 | 现有能力迭代 |
| 机会地图 | 官网及原始招聘平台岗位为主、开源线索补充 | 国内/海外动态切换、城市聚合、可追溯同源岗位列表 | 先做少量平台真实样本和个人收藏验证，再扩覆盖 |
| 投递管理 | 已选岗位、材料快照、操作确认 | 投递状态、下一步、结果反馈 | 先跟踪，后辅助填表/投递 |
| Offer 决策 | 真实 Offer 条款、个人权重和红线 | 场景对比、未知项、待追问条款 | 有真实需求时可做轻量版 |
| OB/VS Code 插件 | 用户选择的笔记或项目成果 | 待归档证据/待确认 Fact | 主闭环稳定后择一 |

对话示例：“我每周只有 6 小时，想补一份目标 JD 中的数据库性能分析能力。先看看我现有项目能证明什么，给我 7 天安排，周末测一次。”

系统应输出已有证据、未确认问题、最值得解决的一个缺口、时间预算和计划提案；用户接受后才成为正式计划。不能只是生成一篇长建议，也不能没有同意就把全部既有任务覆盖。

## 5. 画像、性格与爱好的边界

先做偏好访谈：喜欢的任务类型、成就感来源、协作方式、反馈风格、可承受风险、地域、出差/加班接受度、时间与学习习惯。每项允许用户修正、删除或标记暂不确定。

性格/兴趣可以影响项目题材、学习节奏、沟通方式和探索选项。例如喜欢游戏可以把性能实验包装为游戏排行榜服务；不应因此判定用户只能去游戏公司。

未来可评估自愿使用的兴趣/人格量表，但需核实量表本身的许可与适用范围。AI 从简历和对话推测的标签与用户自报偏好分开保存，不用 MBTI 或少量聊天推断职业天花板、心理诊断或就业资格。

## 6. 能力模型、JD 匹配与缺口诊断

每项能力区分“用户自评”“履历/作品证据”“测评观察”“最近使用时间”。某技术出现在简历、学完课程、刷过相似题，分别代表不同信息。

JD 拆为：工作内容、技术能力、业务领域、级别/影响范围、语言、硬条件、加分项、地域/远程/工作授权、未披露项。保留来源原句和提取时间；职位名称相同不代表要求相同。

先处理硬条件：明确满足、明确冲突、未知待确认。再给分项覆盖和证据质量；总分只辅助同一规则版本中的排序，不表示录用概率。未披露薪资/工作授权不能按“不满足”处理。

缺口至少分为：

| 缺口类型 | 典型情况 | 对应动作 |
|---|---|---|
| 证据未整理 | 做过，但没有可以讲清的故事/成果 | 回顾项目、补基线和贡献界限、整理证据 |
| 表达不足 | 能做但讲解散乱，英文复述困难 | STAR 练习、追问、英文讲解和反馈 |
| 知识不扎实 | 会使用，解释不清关键机制 | 定向章节、概念复述、变式题 |
| 实践不足 | 只学过，没有验证过 | 小项目、实验、复现、设计取舍 |
| 岗位条件差异 | 年限、地点、签证或语言要求 | 核实条件、换目标或设置过渡路线 |

计划不把几十份 JD 合成无限要求。初期只选一个目标方向、1–3 份用户认可的 JD，识别一项最值得补的缺口；有数据积累后再做多个目标的比较与市场需求统计。

本轮用户已选以现有工作经验和主技术栈补强为主。先复用已有项目可证明的能力，再安排证据整理、表达练习或实际补课；不能因为参考资料偏某语言、AI 热点或某类岗位，就自动替用户更换主方向。

学习计划引用具体 JD 版本、缺口条目与当时的履历/测评证据。JD 更新或失效只触发重新评估建议，不能静默改写已接受的计划；新增技术关键词也不自动变成必须学习的任务。

## 7. 学习、契约、测评和口语闭环

采用“较长目标方向 + 7 天可执行承诺 + 每次反馈调整”的滚动机制。正式计划有版本、估算时长、依赖、交付物、验收标准、替换关系；新提案不能悄悄覆盖已接受版本。

每个任务至少说明：为什么学、对应哪个缺口、学哪个具体片段、投入多久、做什么产物、如何检查、未通过怎么办。资料最多先给 1–3 个主要入口，优先官方文档和经过审核的练习，而非批量输出几十个链接。

契约模式包括约定的时间窗口、提醒、专注计时、到点复盘、漏学后的降负荷/改期、阶段测试。签到仅是行为记录；交付与验收才代表任务完成。支持请假、暂停和退出，避免漏一天后无限累积补课债务。

Web 关闭、设备休眠时不能承诺提醒必达。可靠后台提醒需在产品选择时明确采用本地常驻组件、系统日历或后续移动端通知；本轮不创建实际提醒或自动化。

测评先采用达到/部分达到/未达到和具体原因，保存题目版本、rubric、用户答案/产物、检查方法与时间。可确定执行的测试、AI 评阅和用户自报必须分开。复测用变式或延迟复测，减少背答案形成的假提升。

编程练习从解释、输出预测、代码审阅和用户已有项目的小实验开始；若后续执行任意用户代码，使用隔离执行环境，不给用户代码直接访问模型 Key 或私有事实库。

模拟面试分四条能力线：真实项目追问、技术/系统设计、行为故事、语言表达。先做文字轮次，再加入语音输入输出。英语反馈优先关注信息准确、结构、术语与可理解性，不以口音接近某地区作为核心标准。语音记录是否保留与使用哪个服务应可选择。

完成课程或 AI 表扬不自动增加简历事实。只有形成可审查的真实作品/行为和结果，才生成带证据的 Fact 提案，用户确认后入库。

## 8. 机会来源、国内外场景和投递路径

招聘场景应作为组合条件：校招/实习/社招，国内/海外，现场/混合/远程，职能、级别、语言和工作授权。切换国内/海外不只是换地图，也会影响简历习惯、申请材料、语言练习和 Offer 比较条件；具体国家/公司规则保留原文依据，不一刀切。

### 用户确认的数据来源优先级

公司招聘官网和原始招聘平台（LinkedIn、51job、BOSS、猎聘等）是主数据来源；开源清单提供补充发现与线索。个人收藏是用户工作区与早期验证入口，不是正式机会地图的唯一数据范围。

保存“从哪里发现”与“在哪个原始页面取得岗位详情”两层来源。例如通过开源列表发现公司官网职位，发现渠道仍记开源仓库，详情来源记公司官网，两条原链接均保留。只有公司/批次入口而无完整岗位详情的内容先作为线索，不自动计入完整职位总数或参与深度 JD 匹配。

“原始招聘平台”不等于“企业官网已核验”。平台记录须区分发布主体为企业、猎头/中介或未知，认证/官网交叉核验单列；平台名、开源 confirmed 标记或 AI 判断均不能自动赋予官方认证。

每条来源观察至少记录：平台名称、原始 URL、源岗位编号、原文发布时间（若披露）、原文更新时间（若披露）、首次发现时间、本次采集时间、最近核验时间、岗位状态与核验方法。保留原时区与原始时间文案，显示时间以用户界面时区呈现。

源只写“3 天前”时，可保留原文并以观察时间给出明确标注的估计，不能伪造精确发布时间；“刚刚刷新”“HR 活跃”“首次发现”“开源更新时间”都不能冒充首次发布。源未披露时显示“平台未提供/待核实”。

同岗在官网和平台出现不一致的薪资、地点或状态时，保留各来源的值与时间，标记冲突和当前摘要采用依据；官网优先用于核验身份/岗位编号，不能无条件覆盖较新的平台变更。接入方式和可持续性逐平台实测，不因来源优先级已确定就宣称统一 API 或全站覆盖已存在。

| 来源/平台 | 第一接入方式 | 后续可评估 | 本轮核实边界 |
|---|---|---|---|
| 用户已有 JD/链接 | 粘贴、文件导入、手动收藏 | 读取用户明确选择的页面片段 | 最适合先验证闭环，无需等全站聚合 |
| 公司官网 | 保存原始招聘链接和岗位编号 | 稳定公开接口/招聘系统适配，按源独立验证 | career-ops 的腾讯工具等有实现可读，不等于已验证所有公司官网 |
| BOSS 直聘 | 手工/用户登录态页面采集 | 评估 career-ops bookmarklet + 本地收件箱模式 | 采集、聊天、投简历是不同动作；不假定存在可直接用的全量开放 API |
| 51JOB / 猎聘 | 用户提供链接、页面片段和手动状态 | 单平台试点后再做适配 | 本轮未证实可以直接复用的完整稳定接入器 |
| LinkedIn | 公开链接/用户选择的岗位内容 | 上游 guest 搜索工具作为实验候选；官方或用户可用渠道独立核验 | 工具实现不能证明在用户网络、地区、登录条件下长期可用 |
| 海外公司 ATS | 官方申请链接、页面解析 | 按 Greenhouse/Lever 等实际系统评估公开接口 | 链接可见不等于任意岗位可一键最终提交 |
| Simplify / 秋招聚合 | 作为有来源的探索入口 | 许可明确后再同步相应结构化数据 | 校招/实习与用户当前社招主线分开；不复制商业扩展能力 |

投递能力分四步推进：保存与跟踪 → 准备岗位专属材料 → 用户发起的辅助填表 → 限定来源与范围的授权投递。读岗位、起草答案、上传简历、发送消息和最终提交分别记录权限和执行状态；自动化范围在真实实现前单独约定。

第一版投递状态可包括收藏、待评估、准备中、待提交、已提交、面试中、Offer、拒绝、关闭。不能把点击申请链接或准备好材料就标记“已投递”；记录外部提交结果、人工确认与材料版本。重试使用幂等标识，避免同一职位重复提交。

## 9. 国内/海外机会地图

参考网站展示的是 Microsoft MVP 社区分布：首页公开 HTML 写明 3,830 位 MVP、105 个国家/地区，并提供 Explore/Directory/About。它证明的是地图与目录的展示思路，不提供招聘市场覆盖或岗位数据。

BetterMe 地图采用同一筛选结果驱动“指标摘要 + 地图聚合 + 岗位列表 + 侧栏详情”，从世界/中国区域下钻到国家、省/州、城市；每一步都能回到列表。国内/海外开关是市场筛选；“海外远程可在国内工作”“海外现场需当地授权”“国内外企/出海”需要分别筛选。

切换市场时，同步更新地图范围/聚合层级、岗位数/公司数、列表、地区选项、当前来源覆盖和对应岗位详情；保留兼容的技术栈/级别/薪资筛选，不兼容的城市条件需明确提示后清理。国内的外资公司仍按工作地点归入国内市场；海外总部不自动使岗位归入海外。远程机会按允许工作地区独立筛选，不只按发布平台的国家分类。

平移/缩放默认只改变地图视野和聚合层级；只有明确开启“仅看当前地图范围”时才改变查询筛选，并同步数量与列表，避免视野变化悄悄丢失结果。

**2026-10-18 更新：**用户已将全球 3D 地球和国内 3D 地图纳入正式体验目标，替代此前“二维先行、三维后置”的建议；二维 / SVG / 列表保留为兼容降级。最新契约、技术候选与验收以 [岗位地图架构方案](job-atlas-architecture-2026-10-18.md) 为准。地图数据、中文地址、坐标转换、服务配额与真实设备视觉仍需逐项验证。

早期原型可用用户保存的真实职位验证交互；正式机会地图以逐步接入的官网及招聘平台数据为主，开源线索为补充。只有建立稳定更新任务和覆盖说明后，才称作机会聚合地图。没有足够数据时保留列表和来源覆盖提示，不用随机数字或模拟热力图冒充实际市场。

### 必须定义的统计口径

- 分开显示去重后的职位条目数、公司数、地点条目数、符合当前目标条件的职位数；招聘人数只有原始信息明确时另列，未知保持未知。
- 同一岗位来自多个平台时保留多个来源观察，只计一个 canonical job；不能只凭“同公司+同标题”合并不同级别/部门岗位。
- 多城市职位在每个适用城市可出现，但全局职位数仍按唯一岗位计；显示“多地点岗位会重复出现在城市统计中”，不直接把城市数相加当全局总数。
- 远程岗位保留允许工作国家/地区和时区要求，进入独立远程统计；不把公司总部当作实际工作地点。
- 地点未知、岗位失效、来源未覆盖分别表示；没有数据不等于当地没有岗位。
- 统计只覆盖当前接入来源和筛选条件，区分原始发布、源更新、首次发现、采集与最近核验时间；逐条展示当前状态、核验方式及范围。
- 每条岗位可查看原文、原始地点、归一化地点、来源和更新时间；地图数量必须能追溯回列表。

先展示“我收藏了哪些机会、集中在哪、哪些适合我”，有稳定数据后再扩展“某城市岗位增长、技术需求趋势、竞争与薪资分布”。趋势需要可比较的历史快照和覆盖范围，不能把一次抓取的数量称为增长。

## 10. Offer 决策

轻量版支持手工输入 2–3 份真实 Offer。AI 帮助识别缺项、提炼追问、比较取舍，最终选择由用户决定。

| 维度 | 必须区分 |
|---|---|
| 收入 | 币种、工资周期、固定薪资、发薪月数、目标/保证奖金、一次性签字费 |
| 股权 | 归属时间、兑现/流动性、行权成本；不当作当前现金等价物 |
| 成本 | 税费估算的地区/年度假设、住房/通勤/搬迁/保险；税前与税后不混比 |
| 条件 | 试用期、远程/混合约定、工作授权、搬迁要求、奖金追回条件等原文 |
| 发展与生活 | 实际岗位内容、经理/团队信息、可积累能力、稳定性、个人偏好 |

先检查个人红线，再做权重可调整的多维比较。支持保守/基准/乐观情景，展示哪些未确认条件会改变结论、权重调整是否导致排名翻转；不输出伪精确的“最佳 Offer”确定答案。

## 11. Agent 的工作方式与共享数据

先做一个持续对话的协调 Agent，调用类型明确的能力：读取事实、提取 JD、诊断缺口、提出计划、调整任务、组织测验、整理故事、生成简历提案、比较机会/Offer。不同能力可以使用不同提示词/工具，但不需要首期部署大量互相对话的 Agent。

每次有状态改变的操作都应有对象、理由、依据、提案差异与状态。对话可以直接回答问题；需要变更正式计划或事实时生成可接受/拒绝/修改的 Proposal。工具出错保留真实失败状态，不能用“解析成功”掩盖静默降级。

### 领域对象建议

| 对象 | 作用 |
|---|---|
| Fact / Evidence | 已确认经历与原始/派生证据，来源、时间、版本、可见范围 |
| Profile / Preference / Goal | 用户自报偏好、硬约束、可用时间、目标市场/岗位/截止日 |
| Skill / SkillAssessment | 技能别名、证据、测评观察与新鲜度，不与 Fact 混为一物 |
| JobPosting / SourceObservation / JobLocation | 去重后的机会、多来源原始观察、工作地点/远程资格 |
| Requirement / Gap | 有原句的岗位要求、差距类型、优先级和不确定性 |
| LearningPlan / Task / CheckIn | 计划版本、任务依赖/验收、行为记录和调整 |
| Resource | 来源链接、章节、语言、难度、许可、最近核验时间 |
| Assessment / InterviewSession | 题目与规则版本、回答/产物、可定位反馈、复测记录 |
| ResumeView / ResumeArtifact | 从 Fact 派生的岗位定制视图、导出快照和引用的事实版本 |
| Application / Offer | 外部动作与结果、材料版本、条款及对比假设 |
| Proposal / ActionExecution | 待确认变更、接受/拒绝、工具执行结果、授权和幂等标识 |

不需要首期实现所有对象；先把 Fact、Goal、Gap、Plan、Task、Assessment、Evidence、Proposal 的最小关系做正确。

### 记忆的分层

长期事实、可编辑偏好、阶段目标、当前任务状态和聊天摘要分开。聊天摘要仅帮助恢复上下文，不成为事实或计划的第二主库；模型每轮只取得当前任务所需信息。

外部 JD、网页和资料均为不可信内容，只作为要分析的数据，不能通过其中的指令获取密钥、改计划或触发投递。云模型调用会将所需内容发给用户选定的服务商；本地保存不等于所有推理均离线。

## 12. 技术演进建议（待实施选型）

保留现有 TS Core、Schema、存储端口和 React Web；先以模块化单体演进，不因产品模块变多就拆微服务或重写语言。

将系统分成两个数据范围：私人的职业库（事实、计划、语音、简历、投递/Offer）与公开机会/知识索引（许可明确的数据与来源）。公共索引未来可以有可选刷新服务，但不要求上传私人履历；自用阶段可以本地导入和按需拉取。

运行形态要据能力明确：

- 浏览器能承载对话、编辑、OPFS/IndexedDB 存储和手工导入，但受跨域、页面关闭后的调度和执行外部程序的限制。
- 后续的常驻提醒、文件访问、Python/Typst 导出、受控浏览器辅助适合可选本地 companion/桌面工作进程；是否现在引入需按首期验收决定。
- 大规模公共岗位更新需要稳定的任务运行端；可选自托管服务与本地任务都可评估，不能把纯前端页面当成全天候采集服务。
- Web OPFS 与 VS Code/OB 本地文件不是天然同一数据库。引入插件前明确单一写入者、迁移/同步与冲突策略，不允许三个宿主各改一份主库。
- RenderCV 是可选导出 adapter；首期可只生成 YAML 包。学习 Agent 不依赖安装 Python 才能使用。

模型侧继续沿用可配置提供商与薄客户端。先把工具调用、结构化输出校验、可取消任务、失败恢复、成本与来源追溯做清楚；大型 Agent/RAG 框架不是第一阶段的前置条件。

## 13. 插件与多端

插件先当低摩擦采集入口：Obsidian 选中笔记片段提交学习证据/复盘；VS Code 提交用户选择的代码链接、提交记录或项目说明。都进入同一待归档队列，再由用户确认与哪个任务/Fact 关联。

不默认扫描整个 Vault、私有仓库或自动提交工作代码给云模型。复用 schema、ID 和 Proposal 协议，先做单向导入/显式同步。根据用户日常习惯只选一个插件试点，避免同时维护两个完整编辑器与同步系统。

移动端继续保留 Expo 方向；当可靠提醒、通勤学习、口语练习成为真实使用瓶颈时再优先化。聊天入口、通知入口和学习执行环境可以不同，但不能形成多套互不一致的任务状态。

## 14. 原成长路线与验收门槛（后置参考）

以下保留初稿成长阶段设计，不代表当前施工顺序。当前先交付非 Agent 能力，具体批次与门槛以本文开头最新顺序和非 Agent 交付报告第8节为准。

| 阶段 | 范围 | 验收结果 | 明确后置 |
|---|---|---|---|
| 0：修可信底座 | 导入数字/确认状态、新增经历预览、解析降级提示、备份恢复 | 真实简历导入不捏造指标；可追溯未核实项；新经历正确显示 | 不要求先完成所有模板/Word 才能开始成长闭环 |
| 1：最小成长 Agent | 一个目标、1–3 份 JD、对话缺口、7 天计划、3–5 个任务、一次检查与调整 | 用户实际完成一个能力闭环，重开会话可续做 | 海量题库、语音、全平台地图、自动投递 |
| 2：个人机会与求职闭环 | 官网/原始平台真实岗位样本、收藏、可解释匹配、国内/海外二维分布、来源时间、材料版本与基本投递跟踪 | 市场切换后地图/列表/计数一致，能追溯原始平台并用新证据优化材料 | 全站覆盖、无人值守批量投递 |
| 3：面试与语言专项 | 项目/行为/技术文字模拟、语音小试点、变式复测、资料审核 | 反馈能定位到回答/作品，补练后可复测 | 大规模自适应题库和虚构统一能力分数 |
| 4：精选数据源与辅助申请 | 一个国内来源+一个海外/官网来源、增量更新、关闭/去重、限定平台填表 | 样本岗位可追溯、过期可识别、动作不会重复提交 | 默认覆盖所有平台 |
| 5：按真实瓶颈扩展 | Offer 情景比较、一个插件、必要时移动通知/本地工作进程 | 实际减少决策或采集摩擦 | 同时开发全部宿主与复杂云同步 |

Offer 轻量比较与插件顺序可按真实需求插入，不要求等前面所有阶段全部结束。学习闭环是下一阶段主验收；模板、地图和题库数量不能替代它。

### 后置 Agent 阶段的具体使用验收

1. 导入并确认一份真实履历，选择一个目标和一份真实 JD，填写每周可用时间。
2. 对话指出一个优先缺口，显示 JD 原句、已有证据和未知项。
3. 生成 7 天、3–5 个任务的计划；用户修改后接受，保存计划版本。
4. 至少完成一个任务并提交作品、讲解或练习答案；按事先约定的规则检查。
5. 走通一次未达标后的补练和一次漏学后的改期，保持时间预算合理。
6. 最终复测能解释哪些改善、哪些仍未验证；生成下一轮建议。
7. 若确有可对外陈述的新成果，提出引用证据的 Fact 变更；用户确认后用于一份靶向简历。
8. 刷新/重开会话后能恢复目标、正式计划、下一任务、最近反馈；备份可恢复上述状态。

## 15. 调研与验证状态

用户列出的九个 GitHub 仓库/组织均已读取：README、结构、许可证发现情况及针对性关键文件；SimplifyJobs 作为组织读取了两个代表性职位仓库。具体访问证据、版本和限制见 research 文档。

地图示例仅已读首页公开 HTML；浏览器交互授权被拒后未继续尝试打开、截图、点击或通过替代方式验证交互。没有把未观察到的地图行为写成已实测功能。
